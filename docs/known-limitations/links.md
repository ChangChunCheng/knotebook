# Links and links to notes

Typed Markdown links, the "opens in a new tab" icon, links to notes and how links become them, link toolbars and backlinks. Part of [Known limitations](../known-limitations.md).

- **The "opens in a new tab" icon on a link can wrap onto a line of its own.** A link to a web address is followed by a small icon, and a line is allowed to break between the link's text and that icon — so the text can end one line with the icon alone at the start of the next. This is appearance only: the link itself, where it goes and what it is labelled, is unaffected (#153).
- **A few unusual ways of writing a web address get no "opens in a new tab" icon.** The icon is chosen by how the link's address is written: it appears when the address starts with `http:` or `https:` in any letter case (`HTTPS://example.com`), or with `//` (an address with the scheme left out, such as `//example.com`) or its backslash spellings (`\\example.com`, `/\example.com`, `\/example.com`). Some spellings the browser still reads as a web address are not recognized — for example an address that starts with a space or another invisible control character (` https://example.com`), or one with a tab or line break anywhere in it (the browser drops those characters, so `/`, a tab, then `/example.com` is read as `//example.com`). Such a link still opens the site in a new tab when clicked, but shows no icon. A link that has become a link to a note on this site opens in the same tab (see the entries on links to notes below); any other link to a path on this site — for example a public page (`/p/…`), a note address with `?present`, or a link that stayed an ordinary link — still opens in a new tab with no icon. The gap only ever leaves an icon out: it is never shown on a link that does not open a page in a tab, such as `mailto:` and `tel:` (#156).
- **A note's backlinks reflect whoever most recently wrote its outgoing link set, filtered to what *they* could see at the time.** The link index is replaced as a whole (not a diff) — by the editing client when a browser saves the note, and by the server from the content it wrote when an API or MCP write, an applied version, a reverted AI edit or a copy lands — and each target is filtered through the read access of whoever made that write. If an editor with narrower access than a previous editor saves the note, links to notes they can't see drop out of the index — and reappear if someone with broader access edits it again. This is by design (the index follows whoever wrote last, not a ground truth independent of who's editing), not a bug, but it means backlinks can be surprising in heavily-shared notebooks. The one-time link conversion after upgrading to 0.11 only adds links, filtered with the note owner's access (in a group note: notes in the same group) (#106, #269).
- **`GET /api/notes/:id/backlinks` is capped at 200 results (`MAX_BACKLINKS`), most-recently-updated first, with no pagination.** A note linked from more than 200 others silently shows only the newest 200 sources.
- **`POST /api/notes/:id/links` has no rate limit.** Unlike most other write endpoints, this one is deliberately not throttled — its per-request cost is already bounded by the single batched authorization query and the 1000-target cap (`MAX_LINK_TARGETS`), and it's normally called by a debounced background sync, not directly by user action.
- **The note list has no pagination**, and it's the only source used for wikilink autocomplete candidates, for resolving a link to a note's live title, and for converting a pasted, dragged-in or typed link to a note at once (other addresses are looked up on the server) — both effectively cap out at however many notes the list endpoint returns before something has to change. Knotebook's full-text search (the sidebar's search, `GET /api/search` and `search_notes` over MCP, #93) doesn't feed either of them yet; a server-side lookup for wikilink candidates and titles is a future release.
- **Typing a markdown link where the URL contains an unescaped `)` closes the link at that first `)`, leaving the rest as plain text.** Typing `[a](https://x.com/foo)bar)` produces a link to `https://x.com/foo` followed by the plain text `bar)` — the same place a link written this way ends under Markdown's own rules, so it is not specific to typing it live (#99).
- **A typed markdown link only converts when the whole markdown syntax reconstructs back to exactly what you typed — a title, angle brackets around the URL, a trailing space inside the parentheses, or styled display text all block that.** Pasting the same text still produces a link in every case below, but typing it does not, because the conversion insists on reconstructing the identical text before it will act: `[a](https://x.com "title")` (the title is dropped either way, but typing still declines), `[a](<https://x.com>)`, `[a](https://x.com )` (a trailing space before the closing parenthesis), and `[*a*](https://x.com)` or `[**a**](url)` (italic or bold display text). This list is not exhaustive — anything the parser accepts but doesn't hand back verbatim behaves the same way. One case that looks similar but isn't: `[a]( https://x.com )` (a space *before* the URL too) does produce a link, just not through this conversion — Knotebook's editor has its own built-in autolinking that turns a bare URL into a link as soon as a space follows it, so typing that leaves you with `[a](` and ` )` as plain text bracketing a separate link whose text is only the URL, rather than either a clean link or plain text (#99).
- **Typing a markdown link does nothing while a suggestion menu is open** — `[[…]]`, the `/` menu, or any other — and closing the menu doesn't retroactively convert what you already typed; type the `)` again (or just the link text again) after closing it (#99).
- **Backspace right after a link forms usually reverts it to plain text — but a collaborator editing the note anywhere in the meantime cancels that, so Backspace just deletes a character like normal.** In a note nobody else is editing at that moment, pressing Backspace immediately after the link forms reverts it to plain text; whether a following Ctrl+Z then brings the link back, or clears the text you typed since your last pause, depends on whether you paused before that Backspace — pressing it in the ordinary rhythm of typing, with no pause, and then pressing Ctrl+Z clears the run of typing that led up to it (the Backspace and that typing are merged into one undo step), while anything typed earlier, before a pause, is unaffected; pausing at least half a second before pressing Backspace keeps it as its own separate step, so a Ctrl+Z at that point undoes only the Backspace and brings the link back, not plain text. In a live collaborative note, any change arriving from someone else — anywhere in the note, not just near the link — clears the "revert on Backspace" window the instant it arrives; from then on, Backspace after the link just deletes the last character instead. The same applies when the link you typed points to a note in your note list and becomes a link to that note at once (for other addresses, see the entry on links looked up on the server below): Backspace right after it forms gives back the typed text, and if you paused before that Backspace, a Ctrl+Z after it brings the link to the note back (#269). This is existing editor behavior, not specific to markdown links (#99).
- **A markdown link won't convert if a wikilink sits inside the `[…](…)` syntax itself — one elsewhere in the same paragraph doesn't stop it.** A wikilink just before or after the link syntax you're typing has no effect on it, but one anywhere inside it — in the display text or in the URL — leaves the whole thing as typed instead of converting. Nothing is corrupted (#99).
- **Typing `![a](url)` character by character never turns it into an image.** This isn't new — typed text never became an image before this change either. Pasting the same text still produces a real image, and so does an AI assistant or API client writing that markdown into a note directly — both go through the same Markdown parser, just not by typing (#99). The address in markdown written by an API or AI client is not checked: it isn't verified to exist or to belong to the note it's written into, and when it points at another note's upload, a signed-in reader sees the image only if they can read that note, and a public page never shows it (#200).
- **A markdown link doesn't convert while you're typing inside bold or italic text.** The link syntax itself carries the surrounding bold/italic formatting, and the conversion deliberately declines to touch text that carries any formatting, so it leaves it as typed — even if you turn the formatting back off before typing the closing `)`, since it's the whole span the syntax would replace that has to be plain, not just its last character. Typing the link syntax entirely outside the bold/italic run converts normally (#99).
- **A markdown link near the end of a very long paragraph can fail to convert once the link's own syntax is close to or past about 500 characters.** Only roughly the last 500 characters of a paragraph are scanned for a link to convert (a limit of Knotebook's own, not the underlying editor); once a paragraph is long enough to trigger that, a link whose own `[display text](url)` exceeds that length gets cut by the boundary and doesn't convert, regardless of how much text comes before or after it. A shorter link syntax elsewhere in a long paragraph is unaffected — this only bites when the link's own display text or URL is unusually long (#99).
- **Typing the closing `()` first and filling in the display text or URL afterwards never turns it into a link.** The conversion is decided on the keystroke that types the closing `)` — so `[abc](https://x.com)` converts however you assemble it, as long as that `)` is the last character you type: typing the brackets first, filling in the display text, then typing `(https://x.com)` at the end still converts. But once a `)` is already sitting in the document — for example after typing the skeleton `[]()` or `[abc]()` and then going back to fill in the brackets or the parentheses — nothing you type afterwards converts it, because you never type that `)` again. Delete it and type it again (or use the "Link" item in the `/` menu) to convert (#99).
- **Turning a link into a link to a note drops its formatting.** When a link to a note on this site becomes a link to that note — when you paste, drag in or type it, when an API or AI client writes it, or during the one-time conversion after upgrading — bold, italic, code, color and other formatting on its text are dropped; the text itself is kept (#269).
- **Two ordinary links with the same address that touch become one link to a note.** The editor joins two ordinary links with exactly the same address and nothing between them into one link (two links to notes, or two addresses of the same note written differently, are not joined) — for example when you paste or drop a link right at the end of a link with the same address — so they become one link to that note whose text is both texts joined. Its text can be changed in the link's toolbar, which opens when you hover over the link or, on a touch screen, press and hold it (#269).
- **A link to a note the writer can't see stays an ordinary link — even for readers who can see that note.** Whether a link becomes a link to a note is decided with the permissions of whoever writes it (for the one-time conversion after upgrading, see the entries below). If the writer can't see the target, the link stays an ordinary link, even when someone reading the note later can (#269).
- **Some links to this site never become links to notes.** A note address with a query (such as `?present`) or with a `#…` part other than `#b-<block id>`, and a public page address (`/p/…`) stay ordinary links. An ordinary link you move or copy by dragging it within the same note in the same tab stays as it is; dragging it into the note open in another tab makes it a link to the note (#269, #352).
- **Dragging a note from the sidebar's Recent or Favorites tab into a note adds the note's title and its location as two paragraphs of their own, each a link to the note.** Each row of those tabs holds the note's title and its location (for example "My notes") on two lines, and dragging it carries both. The paragraph with the location has the location as the link's text. This was measured in Chromium; other browsers were not checked. The same drag already added both paragraphs before dragged links were converted, as ordinary links (#352).
- **A pasted, dragged-in or typed link that the page has to look up on the server becomes a link to a note a moment later.** A link whose address matches a note in your note list by its current address is converted together with the paste, drop or typing. Other addresses on this site — for example an older address of a renamed note, or any address while your note list hasn't loaded yet — are looked up on the server first (up to 20 different addresses for each paste, drop or edit; any others stay ordinary links), and become a link to the note if it is one you can see. If you paused before it changed, Ctrl+Z turns it back into an ordinary link, which then stays an ordinary link. If it changed right after you made it, Ctrl+Z can remove the link together with its conversion (#269).
- **An ordinary link whose text is a single character can't open its toolbar.** The editor finds the link under the text cursor or the mouse by looking at a position inside the link's text, and a one-character link has none — so neither a mouse hover nor, on a touch screen, a long press opens its toolbar (this comes from the editor component itself). Links to notes aren't affected.
- **A stylus that can't hover has no way to open a link to a note's toolbar.** The long press that opens it on a touch screen only applies to fingers; with a stylus (for example most Apple Pencils on an iPad), tapping a link to a note opens it, and the toolbar for changing its text or target or removing it doesn't appear. Use a finger, or a mouse or trackpad.
- **The toolbar of a link to a note can't be opened from the keyboard.** The arrow keys move the text cursor past a link to a note rather than selecting it, so changing its text or its target, or removing the link, needs its toolbar, which opens only with a mouse hover or, on a touch screen, a long press.
- **The "#" button that copies a link to a heading needs a mouse pointer or the text cursor.** It appears when the mouse pointer is over a heading, or when the text cursor or a selection is in it. Editors can also copy a link to any block, headings included, with **Copy link to block** in the block's drag-handle menu (#269).
- **Writing back a link to a note you can't see, that was deleted, or that is in the trash, turns it into an ordinary link.** Over MCP or the API, such a link reads as `[text](/notes/<id>)` with its own text or the text it was made with; writing that Markdown back saves an ordinary link, because a link is only saved as a link to a note when the writer can see that note. The in-app AI works the same way, without a warning: a link to a note in its result becomes an ordinary link when that note isn't in your note list — you can't see it, it was deleted or is in the trash, or the list hasn't loaded yet (#269). Restoring a note from the trash doesn't turn such links back into links to it.
- **In a group note, the one-time conversion after upgrading only converts links to notes in the same group.** Links in a group note that point anywhere else — another group's notes, personal notes — stay ordinary links; to convert one, delete it and paste the address again, if you can see the note (#269).
- **A link to a block that was later deleted still opens the note, at the top.** The link isn't marked as broken (#269).
- **Over MCP and the API, only a note's current address becomes a link to the note.** A renamed note's previous address, a previous custom URL, and a `/notes/<slug>` link from before 0.3.3 stay ordinary links, even when they still open the note in a browser (#269).
- **Links the in-app AI writes are only matched against your note list.** A link in the AI's result whose address needs the server to resolve it — an older address of a renamed note, for example — stays an ordinary link (#269).
- **Right after upgrading, an ordinary link written into an older note before the conversion reaches that note is converted with the owner's permissions.** The conversion processes the notes that existed at the upgrade one at a time, so on a site with many notes it can take a while. A link to a note on this site written into such a note in the meantime — for example by someone who can't see the target — is converted by it as if the note's owner had written it (in a group note: only links to notes in the same group). The link keeps its own text, if it has one, by the same rules as everywhere else, and each reader still sees the target's current title only if they can see that note (#269).
- **Notes created after the upgrade are not converted.** The one-time conversion only processes the notes that existed when the server was upgraded. Ordinary links in notes created later — content imported after the upgrade, or a copy made of a note before the conversion reached it — stay as they are; new links you paste, drag in, type or write are converted as you make them (#269).
