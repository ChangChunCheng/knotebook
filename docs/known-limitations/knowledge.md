# Knowledge info

Facts a heading carries about what it says: when to read it, a conclusion, a basis, when it was last verified and its status. Part of [Known limitations](../known-limitations.md); how it works is in [Knowledge info](../knowledge.md).

- **Turning a knowledge heading into a paragraph, or merging it into the paragraph above, removes its knowledge info.** **Undo** brings it back; nothing else does.
- **Pressing Backspace at the very start of a knowledge heading turns it into a paragraph, and its knowledge info goes with it.** **Undo** brings it back. (Enter at the start doesn't do this: it adds an empty paragraph above the heading.)
- **Public pages and presentations show no knowledge info.** The server removes it before it sends the note to a public link, and the presentation mode doesn't show it either.
- **Knowledge info can only be added to a heading at the top level of a note.** A heading inside a column, a list or a quote can't carry it. When a knowledge heading is moved into one of them, its info stays in the note but isn't shown; moving the heading back to the top level shows it again.
- **A phone has no drag handle, so the way in is `/info` or the icon.** The `⋮` menu has no entry for it.
- **Tab indents a block in an editable note, so you can't Tab from the text to a status icon while you type.** To open the form from the keyboard, use `/info`. Tab in the first block of a note moves the focus out of the editor, and Tab in a knowledge heading indents it, which takes it off the top level: its icon is no longer shown, and the info stays in the note until the heading is moved back.
- **A heading you change in version 0.17 loses its knowledge info after you go back to it.** Version 0.17 doesn't show knowledge info and drops it from any heading you change there (typing in it, moving it, changing its level or color); headings you don't touch, including ones where you only edit the paragraphs below, keep theirs, and it comes back after upgrading again. See [Self-hosting](../self-hosting.md#upgrading-and-rolling-back).
- **After a change that only turns the heading's text italic or into inline code, the icon can sit a little off for a moment.** The icon is placed when the heading's text, or the size or order of the blocks, changes; a change to the look of the letters alone doesn't trigger that, so it catches up the next time something does, such as typing in the heading or resizing the window.
- **While it is faded, the status icon has a lower contrast than 3:1 against the page.** The icon is faded until you point at it or focus it, so that a note full of knowledge stays calm; pointing at it or focusing it shows it at full strength, and on a screen with no hover it is always faded. The state is also in the icon's name, which screen readers read.
- **In a very large note, typing in a heading is slower.** Every change to a heading works out the knowledge info of the whole note again, so the cost grows with the number of knowledge headings: with several thousand of them, each letter typed in a heading can take tens of milliseconds longer. Typing in a paragraph isn't slowed by your own keystrokes, but each change a collaborator makes arrives as an update that works out the info again, wherever in the note it lands.
- **A very large note is slower to open as a public page if its headings were added or edited since version 0.18, or its text mentions the word "knowledge".** The server then decodes the document, takes the info off and encodes it again on every view; nothing is kept between views.
- **A card that is open while someone else changes the info keeps what it showed when it opened.** Pointing at the icon again shows the new values.
- **If the window crosses the phone width while the form is open, what you had typed and not saved is lost.** On a phone the form is a bottom sheet instead of a card; resizing a window, or turning a tablet, across that width opens the other one with the saved values.
- **A heading can be marked as replaced by one that is itself outdated.** The list of replacements holds all knowledge headings, outdated ones included, and nothing follows a chain of replacements to its end.
- **A version preview doesn't name a replacement in another note.** There it says **knowledge in another note** whatever the other note is; the note's own page shows the name and a link.
- **Searching other notes' knowledge for a replacement draws on the text search budget, and takes longer the more knowledge you can see.** It shares the 60 searches a minute (by default) with the sidebar's text search and `search_notes`, so a lot of typing there leaves fewer for those, and the form says to wait a minute when the budget is gone. Each search looks through every piece of knowledge you can see.
- **A replacement's name can be up to a minute out of date.** A card looks a replacement in another note up once and keeps the answer for a minute; reloading the page asks again.
- **The last verified date can be a date in the future.** Only a date that doesn't exist, such as 31 February, isn't taken: the form asks for a valid date, and a write from an agent leaves it out and lists it as `bad_date`.
- **A last verified date that isn't a valid date counts as no date.** Only an edit made straight through the collaboration editor, not the form or an agent, can store one. Knowledge with such a date and no stored status showed a green check in version 0.18; now it needs review (amber).
- **The index lists at most 2,000 pieces of knowledge from one note.** The index says which note was cut; the rest are still in the note.
- **An index shows at most 5,000 pieces of knowledge at a time.** Beyond that it lists whole notes in the order of the folder sections, and says so; open the index of a subfolder or use a filter to see the rest. Grouping by tag shows the same ones.
- **An index with thousands of rows is slow to show the first time.** All rows are sent in one response, and nothing is paged.
- **When the same knowledge id appears twice in a note, the index lists the first one in document order only, and knowledge whose id isn't in the form the app writes isn't indexed.** The note itself still shows knowledge whose id isn't in that form.
- **A note's index entries can be up to 10 minutes behind after a manual database restore, or after version 0.17 ran for a while.** A background pass every 10 minutes (and one at start-up) brings notes whose index lags behind up to date; it doesn't show a notice while that is pending.
- **Only members of a space can open its index.** Someone who has only been shared a note gets **Index not found**, and notes shared with you, and **Shared with me** and its folders, are in no index.
- **After the first piece of knowledge is added to a folder, its index button waits for the note list to refresh.** Reload the page, or wait for the sidebar to refresh itself.
- **Changing the index's filters adds no step to the browser's history.** **Back** returns to the page before the index, not to the previous filter.
- **A colored collapsible knowledge heading reads without its comment.** It is read as a block of HTML, which has no place for the comment. Rewriting the part it is in, with `edit_note` or a file, removes its knowledge info, and the reply lists it in `knowledge.removed`.
- **A knowledge heading with no text reads as `## ` and comes back as a paragraph.** The markdown parser doesn't read a heading with no text as a heading, so rewriting the part it is in leaves a paragraph that holds `##`, and the knowledge info goes with the heading.
- **The rule that keeps the knowledge info of a heading sent without a comment goes by level and text only.** A heading whose text you changed needs a comment of its own. When the part a write replaces has several headings with the same level and text, the info can end up on a different one of them than the one it was on, for example when an earlier one is removed in the same write.
- **A write whose markdown has a `<plaintext>` tag ignores every knowledge comment in it, the ones before the tag too.** The reply counts them in `ignoredComments`.
- **Stored knowledge info that wouldn't pass today's checks stays as it is until it is changed, except a status or basis.** That covers a value only the collaboration editor could store, such as a `superseded_by` with a space at either end (the web form removes the spaces), and a basis option the site has hidden since. A value written back unchanged is accepted; only a value that changes is checked, and one that fails is left out and listed in the reply's `ignored` while the stored value stays. A stored status or basis that isn't valid at all is the exception, described in the next item.
- **A status or basis that only a crafted collaborative edit could store is dropped the next time an agent rewrites that heading, even when the heading is sent without a comment.** The value is listed in the reply's `ignored`, and the note's fingerprint changes although the markdown sent didn't touch the knowledge.
- **Knowledge info with a NUL character or an unpaired surrogate in a value can be read but not written back.** Only the collaboration editor can store such a value, in a built-in or a custom field; a write that carries it is refused with `invalid_knowledge`.
- **A file sent back whose only change in a place is a knowledge value that gets left out still writes that place.** The place is counted in `applied`, not `same`, so that the reply can list what was left out, even though no stored value changed.
- **The form keeps the status it showed when it opened for knowledge saved without a status.** Such knowledge, saved by version 0.18 or earlier, reads as verified while it has a last verified date. If someone clears that date while your form is open and you then save a change to another field, your save writes the status **Verified** the form showed, so the knowledge stays verified with no date.
- **With Last verified turned off, an agent that leaves `status` out of a comment gets a status worked out from a date it can't see.** Knowledge that has a stored last verified date reads as verified, even when it was outdated; knowledge without one needs review. Writing `status` avoids it.
- **A field turned on after an agent read a note is emptied when the agent writes that part back with a comment.** What the agent read had no line for the field, and a comment without a line for a field that is on means the field is empty. A heading sent without a comment keeps its values.
- **A page that is already open keeps the knowledge field settings it loaded until it fetches them again.** It fetches them when the window comes back into focus, or the connection comes back, at least a minute after it last loaded them, when you open a note or an index whose settings it hasn't loaded in the last minute, and when you reload. Until then, after an admin changes the settings, the form, the card and the index there follow the old ones.
- **When two admins edit the knowledge field settings at once, only newly added options and custom fields are protected.** A save that leaves out an option or a custom field the other admin added in the meantime is refused, and the page loads the latest settings and asks to make the changes again. Any other change the other admin saved meanwhile — turning a field or an option on or off, renaming, hiding or moving an option — is overwritten by the later save without a warning.
- **When two people save different custom fields of the same knowledge at the same moment, only one of them keeps its custom values.** All the custom values of one piece of knowledge are stored together, while each built-in field is stored on its own. When two saves meet before either has reached the other's page, the custom values of only one of them are kept, and the other save's custom changes are lost; changes the two made to different built-in fields are both kept. A save made after the other one has reached your page keeps both.
- **A person written back by an old handle is left out, or names whoever has that handle now.** A changed handle frees the old one. An agent, a file sent back or an AI action that writes a person back by the handle it read before that person changed it gets `unresolved_member`, and the field keeps the person it had; but if someone the writer can name has taken the old handle since, the field names them instead. A copy of a `mergeable: false` note downloaded before the change can't send back only a new `title` either: it answers `409 base_unavailable` with `reason: "note_changed"`, because the note now reads with the new handle. Read or download the note again.
- **Custom fields can't be deleted, only turned off.** Their keys are never used again, so a value stored under a key can't be read as another field's. A site has at most 100 custom fields, turned-off ones included; once it has 100, no field can be added.
- **Custom field values are lost on headings changed after rolling back to version 0.18.** Version 0.18 has no place for them: it doesn't show them, and a heading changed there, by a person or an agent, can lose them. Headings left alone keep them. Restore the backup taken before the upgrade instead of rolling back once anyone has saved knowledge info (see [Self-hosting](../self-hosting.md#upgrading-and-rolling-back)).
- **The form doesn't hold custom values to the total size agents are held to.** Agents can write at most 65,536 characters of custom values for one piece of knowledge, counted as stored, and a value that would go over is left out as `too_long`. The form doesn't check that total, so it can save more; getting there takes long links full of characters that are stored escaped, such as `"` and `\`, or many values kept in fields that were turned off. Nothing is lost: what is stored stays, and an agent's write keeps it, except a new value that makes the total larger, which is left out.
- **While the knowledge field settings are loading or couldn't be loaded, an AI action in the editor that writes its own knowledge comment without `status` under an outdated heading shows that heading as needing review in the preview.** At those times the result is never applied by itself, so nothing changes unless you apply the preview.
- **A write doesn't repair what is already wrong in the note.** A knowledge id that two headings already shared is left as it is, unless a write sends both headings with a comment naming it; then the one lined up with the old heading keeps it and the other gets a new id (only an id a write adds is renumbered when it repeats), and a heading whose stored knowledge id is a temporary `k_new:…` one is left as it is.
- **A heading you rename and keep the comment of loses its id to a heading above it that carries the same id.** When a write renames a heading, keeps its comment and also sends a heading above it with the same `id`, the id stays with the heading above and the renamed one gets a new id, which the reply lists under `knowledge.renewed`. Don't copy one comment to another heading to avoid it.
- **The `knowledge` lists in an `edit_note` or `create_note` reply have a size budget.** A list that goes over it is cut and the reply carries `truncated: true`; the REST and file replies aren't cut.
