# Accounts and sign-in

Passwords, reset links and invitations, sign-in services (SSO), sessions and managing accounts. Part of [Known limitations](../known-limitations.md).

- **A flood of distinct accounts or addresses can push an active login lockout out of memory.** The failed-login throttle keeps at most 10,000 records per track (account and IP), evicting whichever record's last failure is oldest — so an attacker who can produce more recent failures across that many distinct keys, faster than the locked-out record's backoff window (at most 15 minutes), can drop someone else's lockout. Doing so costs thousands of requests from many distinct source addresses, since the attacker's own address gets locked out after 5 failures and every attempt still pays for a password hash. The bound itself is not optional: without it the tables grow for the life of the process.
- **Email matching is case-insensitive; only new writes are stored lowercased.** Every account-writing path (self-registration, accepting an invitation, environment-variable admin bootstrap, OIDC auto-provisioning/linking) normalizes the address to lowercase before writing it, and every lookup (login, sharing, OIDC account linking) compares via `lower(email)` — so `alice@example.com` and `Alice@example.com` now resolve to the same account. The one caveat: this doesn't retroactively merge any pre-v0.1 rows that already exist as separate accounts differing only by case (from before this normalization was in place). Those remain two distinct users; `lower()` matches both at once, and login/sharing deterministically fall back to the older row (see the duplicate-row runbook below), while OIDC linking refuses to guess and rejects with `oidc_conflict` instead. If you're setting up a fresh instance you'll never hit this — it only matters when carrying over data from a database that predates case-insensitive matching.
- **Resolving pre-v0.1 duplicate email rows (e.g. `alice@example.com` vs. `Alice@example.com`).** If two `users` rows exist whose emails differ only by case, `lower(email)` lookups hit both: `POST /api/auth/login` and note sharing pick the older row deterministically (`ORDER BY created_at, id LIMIT 1`) and silently ignore the newer one, while OIDC login/linking rejects with `oidc_conflict` (`multi_email_match`) rather than guessing which one you meant. Detect duplicates with:
  ```sql
  SELECT lower(email) AS normalized, array_agg(id) AS user_ids, array_agg(email) AS raw_emails
  FROM users GROUP BY lower(email) HAVING count(*) > 1;
  ```
  Fix by picking one canonical row per group — the older one, to match the login/sharing behavior above — migrating anything owned by the other row(s) (owned notes' `owner_id`, `note_shares` rows, etc.) onto it, then either deleting the now-empty duplicate row(s) or renaming their `email` to something outside the group so it stops colliding. Finally normalize the canonical row's own `email` to lowercase (`UPDATE users SET email = lower(email) WHERE id = '<canonical-id>';`) so it matches what every write path stores today. There's no automated migration for this in v0.1 — it's a manual, one-time cleanup for instances carrying data forward from before case-insensitive matching existed.
- **Resetting someone else's password takes an admin and a link they send themselves, and it doesn't sign out the person's API tokens.** There is no email and no self-service "forgot password": an admin creates a one-time link in **Site admin → Users** (valid 1 to 24 hours) and passes it on. Completing a reset signs out the person's other browser sessions but doesn't revoke their API tokens or connected apps — revoke those separately in Settings → Authorization if the account may be compromised. An admin can open the link they made, in a browser where they are signed out, and set the password themselves; nothing prevents that, but it isn't silent: the person's other browsers are signed out, their old password stops working, and the server logs both creating and using the link. Self-service password change has a UI now (**Settings → Sign-in**, reachable once signed in via the user menu; any account still flagged to change its password — such as an account an admin created with a temporary password in **Site admin → Users** before invitations replaced that, or, on instances set up before this change, an env-bootstrapped admin that hasn't changed its password yet — is instead routed to the standalone `/change-password` page automatically when they sign in, with a password or through SSO); changing it yourself needs your current password.
- **A password reset link or an invitation link can end up in browser history or in a chat.** The link keeps its token after a `#`, which the browser doesn't send to the server, and the reset page and the invitation page (`/register` with a link) remove it from the address bar as soon as they load. But before that, the address may already have entered the browser's global history, and it stays in whatever chat tool or email carried it. It works once and for at most 24 hours (an invitation, at most 7 days); cancel an unused reset link, or revoke an unused invitation, in **Site admin → Users** if it went to the wrong place.
- **Password reset links and invitations share two in-memory limits, and neither one is what stops guessing.** Invalid links of either kind are limited to 30 per minute per IP together (`ONE_TIME_LINK_MISS_LIMIT`; then `429 too_many_requests`), and completing a reset or accepting an invitation is limited to 10 attempts per hour per link (`ONE_TIME_LINK_ATTEMPT_LIMIT`). Both reset on restart. The first doesn't reduce database work and doesn't hide whether a guess was right — a valid link is never blocked by it. What protects a link is that its token is random, 256 bits long, and can't be guessed; the first only changes the answer (`429` instead of `410`) for a client that keeps sending invalid links. The second only matters to someone who already holds a valid link and keeps sending requests that fail.
- **Admins cannot delete user accounts, only disable them.** Account deletion (including note ownership transfer) is not implemented yet; tracked in [issue #73](https://github.com/sw-willie-wu/knotebook/issues/73).
- **"Online" in Site admin → Users means recently active, not connected right now.** The **Last active** column holds the last time someone used the site while signed in — a browser request to an endpoint that requires being signed in, opening a note for live editing (as a read-only viewer too), a change they make to a note over that live connection, or signing in — and shows **Online** while that time is less than 5 minutes old by the clock of the browser showing the list. It is worked out when the list is drawn — nothing re-checks it on a timer, so a list left open can keep showing **Online** after the 5 minutes are up. Requests made with an API token or a connected app (MCP) don't count, nor does coming back from linking a sign-in service in Settings, nor just having a page open: someone who leaves a note open without typing or otherwise using the page drops out of **Online** 5 minutes after their last activity. To keep writes down, each server process records an account at most once a minute, and the database skips the write while the stored time is less than a minute old, so with one server process the time shown usually trails someone's latest activity by less than a minute and someone who keeps working stays **Online**; with several processes it can trail by more, because each process counts its minute on its own (the database check still allows only one write per account a minute, and each process tries at most once in that time). Activity while another change to the same account is in progress, or while the database can't be reached, can go unrecorded, and that process doesn't try again for that account for a minute.
- **Shortening the web sign-in period doesn't sign anyone out.** The period set in Site admin → Sign-in → Session and tokens is read when someone signs in (and when a changed, newly added or reset password starts a new sign-in), and that sign-in keeps the end time it was given; only sign-ins from then on use the new period.
- **Switching identity providers means linking each person again.** Sign-in identities are keyed on the identity provider's issuer and subject (`sub`), not on email. When people start signing in through a different identity provider, an account whose email matches is not taken over automatically: each person is asked to prove the account is theirs — with its password, or by signing in with a sign-in service already linked to it — before the new identity is linked. Someone whose email doesn't match any account gets a new, separate account while that sign-in service has **Creates accounts** on (otherwise the sign-in is refused). Someone whose account has no password and whose only linked sign-in service has been turned off can't do that alone; the site administrator has to help.
- **No RP-initiated logout.** Signing out of Knotebook only ends Knotebook's own session in that browser — it doesn't log you out of the identity provider. If your IdP keeps its own persistent session (or you have SSO across other apps), clicking "Sign in with …" again can sign you straight back in without re-entering credentials there. That's expected OIDC behavior, not a bug in Knotebook.
- **OIDC discovery is cached until the sign-in service's settings change or the server restarts.** The IdP's configuration (endpoints and supported algorithms; its signing keys are re-fetched on their own) is fetched once via OpenID Connect Discovery and reused until one of that sign-in service's settings is changed in Site admin (turning it off or on counts) or the `app` container restarts — so after changing the IdP itself, turn the service off and on again or restart; see [Sign-in providers](../self-hosting.md#sign-in-providers).
- **The OIDC login/callback endpoints are rate-limited per-IP and in-memory.** `GET /api/auth/oidc/login` and `GET /api/auth/oidc/callback` (and their per-provider forms, `…/login/<provider id>` and `…/callback/<provider id>`, which share the same two limiters) each get their own 30-requests-per-minute-per-IP limiter — like the other in-memory limiters in [Limits](./limits.md), they reset on restart and can't be shared across instances. Because the two quotas are separate, an exhausted *callback* quota only shows up at the end of the flow: the sign-in starts normally, the user authenticates at the identity provider, and the failure appears when they come back. How trustworthy the per-IP dimension is depends on your `TRUST_PROXY` setting — see [Deployment prerequisites](../self-hosting.md#deployment-prerequisites). Starting "Confirm by signing in with …" on the account-linking page counts against the same per-IP login limit, and a wrong password typed on the linking page counts against the same lockout as the login form for that email. Starting **Link** in **Settings → Sign-in** counts against that same per-IP login limit too.
- **HS256-only identity providers aren't supported — and how that surfaces depends on what they advertise.** Signing-algorithm support is checked in two stages: if the IdP's own discovery metadata (`id_token_signing_alg_values_supported`) lists algorithms but none of them is RS/ES/PS-prefixed (an empty list counts as none, and so does a list of only EdDSA), the sign-in service is treated as unavailable before login even starts (`oidc_unavailable`); if the metadata claims asymmetric support but the ID token Knotebook actually receives back is signed some other way (e.g. HS256) — a mismatch between what the IdP declares and what it does — signature verification fails during the code exchange instead (`oidc_exchange_failed`). See [Sign-in providers](../self-hosting.md#sign-in-providers) for what to configure on the IdP side.
- **Linking a password account to SSO doesn't invalidate the original password.** After linking, both password login (while the site allows password sign-in) and SSO login work for that account going forward. There's currently no way to disable password login for a single SSO-linked account. A password the account holder no longer remembers can be replaced only through an admin's reset link (see "Resetting someone else's password" above); there is no self-service way.
- **Signing in returns you to the page you were trying to open — unless you have to change your password first.** When you land on the login page because a page needed a session, Knotebook remembers where you were headed and sends you back there after you sign in, over both password and SSO login. The one gap is a forced password change: an account flagged to change its password (such as one an admin created with a temporary password in an older version) is routed to the change-password page, and after changing it they land on the home page rather than the page they originally asked for. Signing out, and a session that expires while you have a note open, also drop the destination on purpose — the first because leaving is the point, the second because the note page navigates away before the guard runs.
- **Only same-site page paths are honoured as a return target.** The remembered destination has to be a path on this instance that maps to an actual page, at most 2048 characters, made of plain printable ASCII — non-ASCII characters have to arrive percent-encoded, which is what a browser sends anyway. A full URL to another site, an `/api`, `/oauth` or `/.well-known` path, the login page itself, the registration page or the account-linking page, or anything carrying a control character is silently ignored and you land on the home page instead. The same rule is applied twice on the SSO route: once when the destination is stored and again when you come back from the identity provider, so tightening the rule never resurrects a destination that was remembered under an older one.
- **Starting SSO sign-in in two browser tabs at the same time can fail both of them.** Both tabs share the same OIDC state cookie (scoped to the browser, not the tab); starting a second "Sign in with …" before the first completes overwrites that cookie, and the callback route clears whatever cookie it finds on the way in — so either tab's callback can land after the other has already consumed/cleared it and fail with `oidc_state_mismatch`, including the one you started first. Sign in via SSO from one tab at a time.
- **The account-linking page tells someone that an email has an account.** When a person signs in through an identity provider whose email matches an existing account, the linking page — or the error shown when that account can't be linked — confirms that this email has an account here, the same thing a "this email is already in use" message would reveal. The registration form does exactly that: `POST /api/auth/register` answers `409 email_taken` when the email already has an account, so anyone can use it to check whether an email is registered here (each IP gets 10 attempts per hour, in memory like the other limiters in [Limits](./limits.md)).
- **The account-linking page shows which ways the account can be proved.** Anyone holding an identity-provider account with the same email sees whether the Knotebook account has a password and the names of the enabled sign-in services linked to it (leaving out one for the identity provider they just used). It does not show whether the account is disabled, or whether it is already linked to another identity at the same identity provider — those only come out after the person has proved the account is theirs.
- **An account with no password can't be linked from the outside when none of its sign-in services can be used to prove it.** That is the case when every sign-in service linked to it is turned off, or when the only one left is for the same identity provider the person just signed in with (for example, an account at that identity provider that was recreated and now has a different subject). The person then has no way to prove the account is theirs, and they get an error asking them to contact the site administrator.
- **"Must change password" is cleared only by changing the password.** An account an admin created with a temporary password in **Site admin → Users** (no longer possible; invitations replaced it) keeps asking for a new password even if its owner signs in with SSO or links SSO to it. This changed in v0.6: before, signing in with SSO cleared it.
- **The identity provider's `email_verified` claim isn't used.** An email the identity provider marks as unverified can still create an account on first sign-in, and identity providers that don't send the claim at all work normally. Linking a new identity to an existing account always needs that account's password or a sign-in service already linked to it.
- **Someone can take a colleague's email and receive what is shared with it.** Registering with a password, accepting an invitation and a first sign-in through an identity provider all create an account with the email given — typed on the registration page or the invitation page, or returned by the identity provider — without checking that the person owns it. If no account has that email yet, whoever registers it first (or uses an invitation link with it) holds the Knotebook account for it, and notes shared with that email, or that email added to a group, then reach them. The site administrator can only disable such an account after the fact; accounts can't be deleted (see "Admins cannot delete user accounts" above).
- **Turning a sign-in service off doesn't sign anyone out.** People who signed in through it keep their session until it expires, and their API tokens and connected apps keep working (a token created without an expiry keeps working until it's revoked). Deleting the service doesn't change that either. To cut someone off right away, disable their account in **Site admin → Users** — that stops their sessions and tokens too.
- **A sign-in service that creates accounts lets in anyone its identity provider lets in.** While **Creates accounts** is on for a sign-in service that anyone can get an account at (Google, gitlab.com), anyone with an account there can create a Knotebook account through it, as long as their email has no account here yet. Keep such a service's **Creates accounts** off and invite people from **Site admin → Users** instead (this needs password sign-in on), or only turn it on for an identity provider that only your people can sign in to.
- **Registering with a password is on by default, upgraded sites included.** With the defaults (**Allow self-registration with a password** and password sign-in both on), anyone who can reach the site can create an account at `/register`. Accounts created this way can use the AI quick actions the site has set up — the site pays for that usage and its quota — and take up upload space; only site administrators can manage the AI providers' API keys, and Site admin never shows a key (only whether one is set). A sign-in service's **Creates accounts** starts off when the service is added (a service imported from `OIDC_*` by v0.6 to v0.15 took over the value of **Allow self-registration with a password** at the moment of the import), and when upgrading, each existing service took over the registration setting the site had before. Together with the email point above, turn **Allow self-registration with a password** off in **Site admin → Sign-in** if you don't need it.
- **Linking a sign-in service from Settings can end on the login page.** If, while you're on the identity provider, that sign-in service is turned off or deleted or the sign-in cookie expires, or if the per-IP limit on coming back from identity providers is hit, you come back to the login page with an error rather than to Settings — you're still signed in.
- **Adding a password doesn't ask you to sign in again, and suspending someone at the identity provider doesn't revoke their password or API tokens.** While password sign-in is on, anyone holding a signed-in session can add a password to an account that has none, the same as creating an API token. When someone leaves, disable their account in **Site admin → Users**: suspending them only at the identity provider leaves a password they added (usable whenever password sign-in is on) and their API tokens working.
- **With password sign-in turned off, the identity provider is the only way in.** If it's down, its client secret expires, or someone is suspended there, they can't sign in to Knotebook. Recovering the whole site needs access to the deployment's settings and a restart (`PASSWORD_LOGIN_FORCE_ENABLE`, see [SSO-only sign-in](../self-hosting.md#sso-only-sign-in)); while that variable is `true`, anyone can sign in with a password, not only admins, and while **Allow self-registration with a password** is on, anyone can also register with a password again — remove it and restart as soon as you're done.
- **Turning password sign-in off doesn't sign anyone out.** Existing sessions, API tokens, connected apps and MCP clients keep working. To cut someone off right away, disable their account in **Site admin → Users**.
- **While password sign-in is off, the account-linking page still accepts passwords.** That is how password users move over to SSO on their own, so guessing a password still has one way in. Wrong passwords there still count toward the lockout for that email and address — the same counters the login form uses while password sign-in is on — and the guesser first needs an identity-provider account with the same email.
- **Turning password sign-in off doesn't remove anyone's password.** Turning it back on makes every password work again immediately — and so does setting `PASSWORD_LOGIN_FORCE_ENABLE=true`, once the server has restarted — including old ones nobody changed.
- **A password account whose email differs from its identity-provider email can't move over on its own once password sign-in is off — unless its owner is still signed in.** The account-linking page only appears on a first sign-in with the same email, and admins can't link a sign-in for someone else. Someone still signed in from before can link one from **Settings → Sign-in** (turning password sign-in off doesn't sign anyone out); otherwise turn password sign-in back on for a while so they can sign in and do that.
- **The check when turning password sign-in off only looks at you.** It requires at least one sign-in service that is turned on and a linked one for the admin making the change. Other admins aren't checked and may be unable to sign in afterwards.
- **Test connection can't check the client ID or secret.** Apart from noting a missing client ID and checking that the saved secret can still be decrypted, it only reads the identity provider's published configuration; it never exchanges a code, so a wrong client ID or secret first shows up when someone tries to sign in — as an error on the identity provider's page or as `oidc_exchange_failed` when they come back.
- **An administrator can still obtain a sign-in service's client secret, just not silently.** Knotebook sends the client secret to the token endpoint that the issuer's configuration names, so changing a service's issuer clears its saved secret and turns it off — a secret entered for one identity provider can't be redirected to another by editing the service. What remains is the slower path: an admin points a service at an issuer they control and waits for someone to enter the secret again. That leaves traces — the text under the service's row says it has no client secret, and the server logs `登入服務的 issuer 被寫入` with the account that did it and the old and new issuer — but nothing prevents it. **The log line's `to` and `hasSecretAfter` fields come from the write itself and are the trustworthy part; `from` is read separately and can lag under concurrent edits.** Separately, **Test connection** and **Check issuer** let an admin make the server send a request to any address it can reach; apart from the issuer a valid discovery document reports and whether it lists `client_secret_post` (shown as a warning), the response isn't shown, but whether it succeeded is. **Administrator is the highest privilege level in Knotebook.**
- **The affected-account counts can be off when a sign-in service has never connected.** Linked sign-ins are matched by the issuer the identity provider reports, which can differ from the one typed in (for example by a trailing `/`). Until Knotebook has read a service's discovery document successfully — at the start of a sign-in through it, or with **Test connection** — it only has the typed value (and changing the issuer drops what it had recorded). The service imported from `OIDC_*` may already have one recorded at import, inferred from existing sign-ins. So the counts shown before turning a service off may be too low when that service has never connected, and the "no other way to sign in" count may be too high when another service that would still let those people in has never connected. Press **Test connection** first.
