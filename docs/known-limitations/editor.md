# Editing notes

Undo and redo, dragging blocks, the heading outline, block handles, custom colors and pasting text. Part of [Known limitations](../known-limitations.md).

- **Redoing across an "undone to empty" boundary while a collaborator is typing can leave a stray empty block.** Redo after undoing a note back to empty works reliably when you're editing alone (issue #100). In the narrow window where a collaborator writes into the note between your undo-to-empty and your redo, the cleanup step deliberately stands down (removing anything a collaborator may now depend on risks losing their work), so the redo can restore your content alongside the placeholder paragraph as a separate empty block. In the paths we have been able to construct, nothing is lost — your restored text and the collaborator's edits are both kept — and deleting the stray empty block by hand resolves it.
- **A collaborator's edits to the blocks you are dragging can be lost.** A block dragged by its ⋮⋮ and dropped above or below another block lands with the content it had when you started dragging, so what a collaborator types into it while you hold it disappears. Dropping it beside another block or into an empty column keeps what they typed. When a collaborator deletes one of the dragged blocks before you let go, the drop brings the deleted block back and an empty paragraph can remain where the blocks were.
- **The editor's collaboration library, y-prosemirror, is patched.** `patches/y-prosemirror@1.3.7.patch`, applied by pnpm at install, puts the cursor at the nearest text when a block selected as a whole is gone by the time y-prosemirror restores the selection, where the unpatched library raises an error and leaves the note out of step with your collaborators' (#428); upgrading y-prosemirror means carrying the patch over or dropping it once the library handles this itself, and `apps/web/src/collab/node-selection-restore.test.ts` fails when it no longer applies.
- **Only headings of level 1 to 3 appear in the heading outline.** Headings of level 4 and deeper are not listed.
- **Tabbing out of the outline to the browser's address bar, or past the end of the page, can leave the floating outline panel open.** The panel closes when focus moves to another element on the page or when you click elsewhere; moving focus out of the page itself does neither. Click elsewhere on the page to close it.
- **Scrolling by hand, or pressing a scroll key outside the outline's list (on its rail or buttons, or while typing), moves the highlighted heading back to where the page actually is.** After you jump to a heading near the end of a note, which cannot reach the top of the page, the outline keeps that heading highlighted until you scroll by hand; the mouse wheel, touch dragging, Page Up, Page Down, Home, End, Space, the up and down arrow keys, and pressing the mouse or a finger anywhere in the scrolling area (the note text, or the scrollbar) all count as scrolling, so they end that early.
- **With the outline pinned, typing a note's first heading, or deleting its last one, makes the text column move or narrow at once instead of sliding.** The column slides between its normal and pinned position when you pin or unpin, or resize the window, but not when the outline itself appears or disappears.
- **On a phone or a window narrower than 768px, the heading outline is reached from a bubble that appears only while you scroll, or from the note's ⋮ menu.** The bubble disappears about 1.5 seconds after scrolling stops, unless it has focus. On a shared public page there is no ⋮ menu, so the bubble is the only way in; screen reader users have to scroll the page to make it appear.
- **Pasting a plain-text file view (a `/raw/` URL) can be parsed as Markdown even when the file is source code.** A browser rendering a `text/plain` document wraps it in a bare `<pre>`, which carries no formatting of its own, so the clipboard cannot say whether that file was a Markdown document or a Dockerfile. BlockNote's Markdown detector then decides, and it fires on incidental syntax: an underscore pair such as `$SERVICE_NAME` or a backticked word inside a comment is enough. Once it treats the payload as Markdown, a leading `# comment` becomes a heading. A code snippet copied from a *documentation page* is not affected — that arrives as a `<pre><code>` block, which Knotebook honours as a code block — and neither is a copy out of VS Code, which tags the clipboard with the file's language. To paste a source file from a raw URL verbatim, insert a code block first and paste inside it: pasting inside a code block always inserts plain text.
- **Pasting a large amount of plain text into an ordinary paragraph is slow in the browser, and very large pastes never arrive.** Plain text pasted into the editor is read as Markdown, so lines that follow one another with no blank line between them (logs, chat transcripts, hard-wrapped text) become one paragraph with a line break at the end of each line, and the browser editor slows down more than proportionally with that shape. Measured on 2026-11-08 in headless Chromium: pasting 1 MB froze the tab for about 6 seconds and each keystroke afterwards took about 0.35 seconds; 2 MB froze it for about 26 seconds, then about 2.8 seconds per keystroke; at 3 MB the tab stopped responding and the text never reached the server. The same text pasted inside a code block takes about a second even at 10 MB. To paste a large block of text, create a code block first and paste into it, or separate the paragraphs with blank lines before pasting. Not planned for this release.
- **On a window between 640px and 767px wide, a block's hover handles are partially clipped.** Below 768px the note text's side inset shrinks to 20px (so the text lines up with the title where horizontal space is scarce), and BlockNote's block handles — the `+` and `⠿` that appear to the left of a block when you hover or tap it — live in that inset and are wider than it, so on such a window they are cut off by the card edge. Windows narrower than 640px don't mount the block handles at all (insert a block with `/` or the editing toolbar), and windows 768px and wider keep the full 70px inset, so the common cases are unaffected ([issue #115](https://github.com/sw-willie-wu/knotebook/issues/115)).
- **On a window narrower than 640px, three block actions have no entry point.** "Copy link to block", "Ungroup columns" and the whole-block color live only in the block handle's menu, and windows narrower than 640px don't mount the block handles. (Headings still show their `#` button while the cursor is inside them, which copies the same link.)
- **A note with thousands of distinct custom colors loads more slowly.** As colors appear in the editor, it adds style rules for each distinct custom color used on a block or table cell, and for each one used in text. In one measurement, 2000 distinct block colors added about 1.7 seconds to the first load; colors inside text, and typing, were not affected. Notes with a handful of colors are not noticeably affected.
