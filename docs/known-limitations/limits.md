# Limits

Note size, parse workers, rate limits and site limits. Part of [Known limitations](../known-limitations.md).

- **In-memory rate limiting and login lockout reset on restart.** Failed-login backoff counters, the password-hashing concurrency semaphore, the password reset link and invitation limiters (invalid links per IP, attempts per link), the collab-token/slug-change rate limiters, and the short-lived gate that lets a just-deleted note report itself as deleted rather than inaccessible all live in process memory; restarting the `app` container clears them. This is also why they cannot be shared across instances — see the [single-instance warning](../self-hosting.md#single-instance-warning).
- **Markdown that takes the server too long or too much memory to read is refused.** The server reads written Markdown into note content in parse workers — threads of their own with their own memory limit — so other people's requests and live editing keep running meanwhile (#398). A write whose Markdown takes longer than `PARSE_TIMEOUT_MS` (default 10 seconds) or more memory than `PARSE_WORKER_MEMORY_MB` (default 1024 MiB) to read is refused with `unsupported_block`, its message saying the content is too complex, and nothing is written. How long and how much depends on what the Markdown holds more than on its size. Measured on a machine of 2 vCPUs and 4 GiB: about 256 KB (the largest write accepted) of ordinary formatted Markdown takes about 1.4 seconds and fits in 256 MiB; the slowest content measured that still fits the defaults is 256 KB of words separated by `<br>` in one paragraph, about 7 seconds and about 640 MiB. Dense formatting inside quotes or `<details>` needs more memory the deeper it sits — 256 KB of bold words inside quotes nested 5 levels needed about 1.5 GiB — and is refused with the defaults; Markdown nested several thousand levels deep runs into the time limit. (Quotes nested 128 levels deep and lists nested 64 levels deep are refused for their depth.) A site that needs such content can raise the memory limit (Site admin → Site limits, up to 3072 MiB, or `PARSE_WORKER_MEMORY_MB`) or, with `PARSE_TIMEOUT_MS`, the time limit; see [Self-hosting](../self-hosting.md#parse-workers). This applies to `edit_note`, `create_note`, `POST /api/notes` with `content`, `POST /api/notes/:id/edits` and files sent back or created over MCP bulk transfer alike.
- **One person can keep parse workers busy, and when every worker is busy, others wait.** Reading the Markdown of a write, putting a write into a note, and turning a note of 16 KiB or more back into Markdown (reading it over MCP or the API, downloading it) all queue for the same parse workers. One person uses at most two workers at a time, and a second only while nobody else is waiting; but on a machine with 2 CPUs the server runs one worker by default, so someone reading very large notes, or sending heavy writes, one after another can make everyone else wait up to a job's time limit each time — three times `PARSE_TIMEOUT_MS` for reading or writing a note (30 seconds by default), four times for a file sent back over bulk transfer. A job that waits longer than `PARSE_QUEUE_WAIT_MS` (by default 4 × `PARSE_TIMEOUT_MS` + 5 seconds, 45 seconds, so that waiting behind one job running to its limit is enough) answers `server_busy` and writes nothing; behind two such jobs it can still run out. Each job counts against the sender's read or write budgets, but those budgets allow enough of them to keep one worker busy. At most 100 jobs wait at once; more answer `server_busy` straight away. Notes under 16 KiB don't wait for parse workers. Live editing in the browser doesn't use them.
- **Putting a large write into a note, and reading a large note back, still hold up the server briefly.** Reading the written Markdown, putting it into the note and turning a note back into Markdown happen in parse workers, but some linear work on the note's stored structure stays in the server's own thread: encoding a note someone has open to hand it to a worker (about 5.4 MB stored: about 14 ms typed straight through, about 173 ms heavily edited), putting the result into the open note, and saving the note. Measured on Linux: with about 245 KB in one paragraph of `<br>`-separated words or of alternating bold and italic, a write held the server up for about 0.2–0.45 seconds (before parse workers did this, 0.6–2.1 seconds); reading a note of 1 MB, or one paragraph of 49 000 such words, back about 0.01–0.15 seconds (before, 1.2–5.3 seconds). Applying a note version, and the one-time link conversion after upgrading, still turn the note around in the server's own thread. Text with a very long run of spaces (which only typing in the editor can make) takes time growing with the square of that run to read back: 100 000 spaces in one text took about 2.2 seconds — now in a worker, so it can run into the time limit above (#398).
- **In the browser the note size limit is only a soft check, and a note can end up somewhat over it.** The server doesn't check live edits from the browser at all. The web editor checks before pasting, dropping content in or applying an AI action's result, using an estimate of how much the note will grow — the text of what is being added plus a fixed amount for each paragraph, list item, table cell and other element, for each piece of formatting (with a link's address) and for long attributes such as a diagram's source, minus what it replaces. Measured against the real growth, the estimate came out between about 0.94 and 1.15 times it for every shape tried (paragraphs, flat and nested lists, checklists, tables, long text, Chinese text, text with formatting or links on most words, pasted code, diagrams), so near the limit a paste can be let through that takes the note a little over it, or refused when it would just have fit. Replacing content with the same content is estimated as no growth, but still grows the stored state a little (the collaborative document's bookkeeping, a few percent of what was replaced), so that is bounded too. Typing isn't checked, so a note can also grow past the limit a keystroke at a time, and undoing a deletion (Ctrl+Z) can put content back. Someone with edit rights who writes their own collaboration client instead of using the editor bypasses the check entirely. Writes over MCP, the API and bulk transfer, reverts, applying a version and copying are checked exactly by the server (`413 note_too_large`).
- **A note over its size limit can still grow a little through MCP, the API and bulk transfer.** Over the limit, a write is judged by what it leaves behind: it is refused if the content still in the note grows, or if the note's stored state grows by more than 4 KiB in that one write. Replacing content with the same amount or less is accepted, but it still leaves bookkeeping behind in the collaborative document — about 40 bytes per replacement, measured — so a note over the limit that keeps being reworded grows by that much each time; deleting content shrinks it again. Formatting text, or changing an attribute to a longer value, adds content and is refused on a note over the limit.
- **The note size limit counts the note's stored state, not its text.** The stored state also holds formatting and the structure collaborative editing needs, so a note is larger than its text, and one whose text was inserted here and there (or by several people at once) is larger than the same text typed straight through — measured, a character inserted in the middle of existing text takes about 23 bytes, one typed at the end about 1. Deleting text frees almost all of its space. There is no way yet to see a note's size in the app; the server logs, when it starts, the ids of notes already over the limit.
- **A tab that is already open can check uploads and note size against an old limit.** The editor reads the upload size limit and the note size limit when the page loads its site settings, and checks a file before sending it, and a paste or a drop before adding it, against that value. After a site admin changes either limit, a tab that is already open keeps the old one until it reads the settings again, which usually happens when you switch back to it; reload the tab to be sure. Meanwhile it can refuse a file the new limit would take, or send one the new limit refuses (the server checks uploads against the limit in force when the request arrives and answers `413 file_too_large`); and it can refuse a paste or drop the new note size limit would take, or let through one it would refuse, since the server doesn't check the browser's edits (see "In the browser the note size limit is only a soft check" above).
- **Changes to the site limits are not passed on between server instances.** The values are kept in memory and read from the database when the server starts, so with more than one `app` process (not supported, see the [single-instance warning](../self-hosting.md#single-instance-warning)) another process uses the old values until it is restarted, and when two processes change limits at the same time, the old value recorded in the list of changes can be out of date.
- **Lowering a rate limit, or raising it again, doesn't reset anyone's count.** The windows already open keep their counts: someone who has already used as many requests as the new, lower number, or more is refused until their window ends. Requests that are refused are counted too, so after a limit is raised, someone who kept retrying while they were blocked may already be over the new number and has to wait for the window to end as well.
- **Changing the memory per parse worker replaces every worker.** The replacement workers take about 0.5–0.7 seconds to become ready, and jobs wait in line meanwhile. A busy worker finishes its job before it stops, so for a short while the old workers and the new ones exist together and use more memory than the formula in [Self-hosting](../self-hosting.md#choosing-the-values) allows for. If a worker had failed to start and the server was waiting before it tried again when the limit is changed, a healthy worker is replaced in that state too: there can then be no parse worker for up to about 30 seconds, and a job that waits longer than the longest wait for a worker (45 seconds by default) answers `503 server_busy`.
- **A very large note can't be read over MCP or the API, or downloaded.** Turning a note into Markdown may take three times `PARSE_TIMEOUT_MS` (30 seconds by default) and as much memory as a parse worker has (`PARSE_WORKER_MEMORY_MB`, 1024 MiB by default). A note that needs more answers `500 too_complex` (MCP: the tool error `too_complex`), and a bulk download leaves it out, listed as `skipped` with `reason: "failed"`. Measured on Linux, a note of 10 MB of ordinary text took about 10 seconds; one dense with formatting gets there sooner. It still opens in the web app. Raise `PARSE_TIMEOUT_MS` (the Site limits page only goes down from 10 seconds) or the memory per worker (`PARSE_WORKER_MEMORY_MB`, or Site admin → Site limits) to read such notes (see [Self-hosting](../self-hosting.md#parse-workers)) (#398).
- **Most `429` responses have no `Retry-After` header or wait time at all.** The exceptions: the `429 too_many_attempts` of `POST /api/auth/login` and `POST /api/auth/oidc/pending/confirm` includes a wait time, but in the JSON body (`retryAfterMs`), not a standard `Retry-After` header; every `429` of the four bulk transfer endpoints under `/api/transfer/` carries `Retry-After`; and so does the `429` that `POST /api/notes/:id/uploads` and `GET /api/uploads/:id` answer once invalid Bearer attempts from an IP are used up. The other rate-limited endpoints — `POST /api/notes/:id/collab-token`, slug changes via `PATCH /api/notes/:id`, `POST /api/notes/:id/uploads`, `POST /api/notes/:id/copy`, `GET /api/notes/:id/content`, `GET` and `POST /api/notes/:id/edits` and `POST /api/notes/:id/edits/:editId/revert`, `POST /api/notes`, `GET /api/search`, the public-link management and public share endpoints (#72), username renames via `PATCH /api/auth/profile`, the API-token limits (per-user token reads and writes, invalid Bearer attempts per IP on the endpoints that take an API token, and `POST /api/auth/tokens`), `POST /api/auth/oidc/pending/prove/:providerId`, `POST /api/auth/oidc/link/:providerId`, `POST /api/auth/register`, and the OAuth endpoints (`POST /oauth/register` 30/hour, `GET /oauth/authorize` 30/min, `POST /oauth/token` 60/min, all per IP) — return a bare `429` with no timing information at all (the OAuth ones as `{error:"invalid_request"}` or plain text); callers must back off and retry at their own discretion.
- **Copying many notes at once from the sidebar stops after about 30 in a minute — sooner if you've made other writes in that minute, or, when the notes have attachments, copied or uploaded many attachments in the last 10 minutes.** Each copy counts against the per-person limit of 30 writes a minute, which is shared with writes through the API and MCP (edits, creating a note with content, and MCP's `delete_note` and `restore_note`), with reverting an AI edit (in the browser too), and with saving, applying, renaming and deleting versions; copying a note's attachments also counts, one per attachment, against the upload limit of 120 every 10 minutes, which uploading files shares. A larger selection stops partway with "Too many requests. Please slow down."; the notes already copied stay copied, and the one it stopped at and those after it stay ticked, so you can try again once the limit has passed — within a minute for writes, up to 10 minutes for attachments. Moving notes into a group or to the trash isn't limited this way, and neither is anything done with folders, which has its own, much larger limit (see [Folders](./folders.md)).
