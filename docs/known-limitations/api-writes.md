# Writing notes over the API and MCP

How writes merge, are recorded and reverted, and what survives a Markdown round trip. Part of [Known limitations](../known-limitations.md).

- **A write can be refused with `server_busy` when someone keeps changing the same section back and forth.** A write from MCP, the API or bulk transfer, and a revert, is worked out in a parse worker against the note as it is at that moment. Changes others make meanwhile to other parts of the note don't matter — the write is merged with them — but if they touch the section the write's `if_match` names (for a whole-note `if_match`, or a file sent back, any part of the note), the write is worked out again, and a changed section then answers `409`. Only when the section was touched but ends up the same, three times in a row, is the write refused with `503 server_busy` (`Retry-After: 5`) and nothing written. A file sent back over bulk transfer needs the whole note unchanged, so steady typing anywhere in a large note can overtake it three times; try again when the typing stops (#398).
- **Typing that happens in the same couple of seconds as an API write is attributed to that write.** The browser saves a burst of typing once, shortly after it stops. An API write saves immediately when it merges, and that save also flushes whatever human typing was still waiting — so the whole batch is stamped with the API write's author and agent label. No content is lost; only "who edited this last" is coarse at that boundary. Reading a note never has this effect: the read path never opens a writing connection at all (#106, #137).
- **A *rejected* API write can swallow the attribution of human typing that was waiting to be saved.** A write that is refused inside the merge (a fingerprint mismatch) still closes its connection, which is also an immediate save — and that save takes the place of the one the human typing had scheduled. The refused write writes no attribution of its own (it is gated on having actually applied something), so the result is that the human batch's "last edited" is simply not recorded. **The typing itself is saved** — only the attribution is skipped, and the next edit restores it (#106, #137).
- **`replace_all` gives every block in the note a new id.** Anything holding block ids from before — a section id you cached, an in-flight edit record, another program's outline — stops resolving. Prefer section-level operations when something else may be addressing the note; after any write, use the fresh `outline` the response returns (#106, #137).
- **An API write can succeed and still not be recorded.** Content is merged into the live document first and the history row is written afterwards, deliberately — no database transaction is held across the merge. If the row fails to be written, the answer is `500` with the content already in the note and nothing in the edit history, so that change cannot be reverted through the API (a retry is refused by its fingerprint instead of duplicating the edit). **A revert fails differently**: the content is already restored, but the revert row is not written and the original row is not marked. That original row then becomes **non-revertable** and pressing revert again answers `409 stale`. The two operation families arrive there differently — for `replace_all`/`replace_section`/`insert_after`/`append` the fingerprint check does it by itself, since restoring replaced exactly the blocks it compares, while `delete_section` (no fingerprint, and an anchor that survives a restore) is caught by a separate idempotency rule: an edit whose original blocks are back at the top level counts as already restored. Without that rule a retry would insert them a second time and leave two top-level blocks sharing one id. Neither shape is fixable by retrying (#106, #137).
- **`POST /api/notes` with `content` can leave an empty note behind.** If applying the content fails, the note row just created is deleted again on a best-effort basis; if that deletion *also* fails, the answer is still `500` but an empty, untitled-or-titled note stays in your list. Delete it by hand (#106, #137).
- **A note's edit history stores a full copy of what each edit replaced, with no size cap.** Every recorded write keeps the blocks it overwrote so it can be undone, so a note that is repeatedly rewritten in full can hold up to 100 complete snapshots of itself. Nothing trims them other than the 100-row window (#106, #137).
- **`revert_of` cascades, so "the last 100 edits" is really "at most 100".** Each note keeps its 100 most recent history rows, and deleting a row deletes any revert of it. Two consequences: reverting the *oldest* remaining edit pushes the pair out together (101 rows, revert the oldest, 99 remain), and an ordinary write's trim can take out a revert row that is still well inside the window, if the row being trimmed happens to be that revert's original. A revert row's lifetime is bounded by its original's. The second path is **deliberately left untested** — constructing it means driving a note to the trim boundary *and* arranging for the trimmed row to be some revert's original, which costs far more than it guards, since the behaviour is the same mechanism as the first path and that one has two cases holding it (#106, #137).
- **The per-note write queue and the editing runtime are process-local, and there is no cap on how many notes are written at once.** The queue only guarantees that two writes to *the same* note are serialised (see the [single-instance warning](../self-hosting.md#single-instance-warning)); writing N different notes at the same time means N concurrent headless editors, each leaving roughly half a megabyte behind that garbage collection does not reclaim, plus the cost of building it. This is the first path where an **external** request drives that work — reading content also builds one, but under the tighter read budget and without writing. Today's only throttles are the per-user write and token budgets; there is no per-process concurrency gate, so the memory ceiling under many simultaneous writers is set by how many requests arrive at once. Capping it would mean a global semaphore, or moving the runtime into a worker thread (#106, #137). Since #398 reading the written Markdown, putting it into the note and reading a note of 16 KiB or more run in the parse workers, so those editors are bounded by the number of workers; notes under 16 KiB, applying a note version and the one-time link conversion still use an editor in the server's own thread, with no cap.
- **A concurrent write is only protected where the target section has content.** The fingerprint the server re-checks at merge time is a constant for a zero-block section, so `replace_section`/`insert_after` aimed at a `_top` with no blocks, any operation on a note with no blocks at all, and `append` sent without `if_match` have no such protection. Nothing is lost in those cases — content the browser inserted during the window is kept — but where the written content lands *relative* to it is decided by the collaborative document (#106, #137).
- **The wikilink index can briefly lag an API write.** Two causes: an API write recomputes the index from the copy it edited, so a link the browser added in the same window may not be in it yet; and the index update itself can fail (a lost race with a later browser update, a busy write, or a database error — the last is only logged as a warning and deliberately does **not** turn an already-applied, already-recorded write into a `500`, since an AI would retry and duplicate the edit). Both fix themselves the next time that note's link set changes or a browser reconnects to it (#106, #137).
- **`POST /api/notes` now rejects unknown body fields.** A field the server does not recognize used to be ignored; it is now `400 invalid_body`. This is a behaviour change for existing callers — and it is deliberate: with `content` accepted, a request that misspells it would otherwise create an empty note and report success (#106, #137).
- **Merely opening an empty note in the browser editor records you as having edited it.** Mounting the collaborative editor in a browser tab on a note with no blocks normalizes it to a single empty paragraph, and that normalization is written back into the shared document over the live collaboration connection, where it travels like any other edit — so a note you only *opened* there, without typing a character, comes back with its last-edited line naming your username, dated the moment you opened it. The server has its own headless mount of the same editor — the one the read path uses to render a note as Markdown — and it performs the identical normalization, but that mount never joins the collaboration session, so the normalization has nothing to write back to and never becomes an edit; the effect described here is specific to the browser's mount. This is emergent from how the editor and the collaborative document meet, not a defect in the attribution itself. ⚠ Derived from reading the code; not confirmed end to end (#106, #137).
- **After a revert is refused, that row keeps offering a Revert button until the dialog is reopened.** The **AI edit history** list is refetched on success only, so a `409` — the note has moved on, or the entry was already undone — leaves the stale row on screen with a button that looks usable; pressing it again just fails again. Closing and reopening the dialog shows the true state. It heals itself, but nothing in the UI says so at the time (#106, #138).
- **A fingerprint is concurrency protection, not permission protection.** `if_match` refuses a write built on a stale read — it says nothing about whether the program sending it has read anything. An `append` sent without `if_match` skips the check entirely, by design. What bounds a credential is its scope (`notes:read`, `notes:write`, `notes:move` for moving or copying into a group, and `notes:delete` for moving notes to the trash and restoring them), the sharing on each note (for a group note, your role in its group), and the fact that most writes that put content into a note are recorded in that note's **AI edit history**, where such a write can be undone — while it is still one of the note's 100 most recent recorded writes and nothing has changed those blocks since. A `create_note` with no `content` records nothing at all (#108). Some writes aren't in that history, for example a `rename` (rename it back instead), `move_note_to_group` (a single note can't be moved back out, and the shares, public link and version history it loses don't come back), `copy_note` (the copy starts with no history) and `delete_note` (`restore_note` brings the note back, while it is still in the trash and only for someone who can restore it).
- **Over the API and MCP, some spaces don't survive writing what you read back, and code can't carry a color.** Spaces at the start or end of a paragraph or a heading don't survive writing what you read back, and in a table cell neither does a space right after a line break. Code formatting can't carry a color, so a colored stretch that comes back as code loses its color (#222).
- **A list or table with block or cell colors reads back as HTML as a whole.** Over the API and MCP, text and background colors can be written as one of the editor's ten color names or as a hex color, among other forms; [AI editing](../ai-editing.md#colors) has what is accepted and what is rejected with `unsupported_color`. A custom color is shown as written, in light and dark mode alike: the editor does not adjust it for contrast. On reading, colored text stays in the Markdown as a `<span>`, but a list with one item that has its own color, or a table with one colored cell, comes back as one block of HTML rather than Markdown; a file attachment's background color and the color of a block with no text are not carried; and a color that isn't one of the ten names or a lowercase `#rrggbb` color — one stored before colors were checked, or left by pasting from elsewhere — is not shown in the editor and reads back as no color, so writing the block back removes it. See [AI editing](../ai-editing.md#colors) (#222, #378).
- **Some image widths don't travel over the API and MCP, and sizes not written in the form reading gives are refused.** An image whose preview is turned off reads back as a link, without its width, and writing that back gives a paragraph with the link rather than the image. An `<img>` with a `width` inside a table cell is refused with `unsupported_size`; this version has no images in table cells. From this version, a `width` on an `<img>` or a `colwidth` not written as [AI editing](../ai-editing.md#sizes) describes, and a `<div>` laid out with `display:flex` or `display:grid` other than a row or column of [side-by-side columns](../ai-editing.md#columns), reject the whole write (`unsupported_size`, `unsupported_columns`) — including text of a colored table with column widths or a colored image with a set width as an earlier version read it. And an image inside a toggle heading or a toggle list item whose address is relative but isn't one of this site's uploads (such as `/static/pic.png`) is saved with the site's full address once that block is written back. A `<figure>` image written inside a quote (`> <figure>…</figure>`) is dropped without an error, leaving an empty quote, because a quote holds only text.
- **Over MCP or the API, a link to a note with no text of its own can still get the note's old title as its own text when it is written back.** Writing back the text that reading showed for such a link, or that you wrote for it yourself, keeps it following the note's title (see [MCP](../mcp.md#links-to-notes)), but the server only remembers each such text for up to 24 hours after the last read or write that had it — less if the account reads or writes more than 10 000 of them in that time, or the site more than 100 000 for everyone together, since only the latest are kept — and forgets everything when it restarts. It remembers only what `read_note_section` (the whole section, also the pages of it you didn't fetch), `GET /api/notes/:id/content` and the `current` in a `409` from `POST /api/notes/:id/edits` or its revert showed to the same account, and the links that account wrote with `edit_note`, `create_note`, `POST /api/notes/:id/edits` or `POST /api/notes` — not what a bulk-transfer download showed, nor links in files sent back. So if the linked note was renamed after you read it and the server no longer remembers that read, writing the link back with `edit_note`, `create_note`, `POST /api/notes/:id/edits` or `POST /api/notes` saves the old title as the link's own text, and the link stops following the note's title; read the section again before writing it. The other way round, text you set on purpose to a title the note had when a read showed it to you, or when you wrote such a link, within those 24 hours is saved as no text of its own, and the link shows the note's current title (#387).
- **`edit_note`'s reply carries fingerprints only for the page its change landed on.** A successful write returns at most 100 sections' worth of per-section fingerprints, starting at the section that now holds what was written (for `replace_section` and `insert_after`) or at the start of the note (for `replace_all`, `append` and `delete_section`). On a note with more than 100 sections, a run of edits that moves outside that page has to go back to `read_note_outline` and `read_note_section` for the next fingerprint (#108).
