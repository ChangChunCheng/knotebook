# Profile pictures

Uploading, cropping and showing profile pictures, and pictures from sign-in services. Part of [Known limitations](../known-limitations.md).

- **A site admin can't remove someone else's profile picture.** Only its owner can delete it (`DELETE /api/auth/avatars/:id`). Disabling an account disables the person, not their pictures: they stay readable, and anyone who is signed in and has a picture's address can still read them. To get one removed, delete its row from the `user_avatars` table in the database; the original file then stays on the server until it is removed by hand (see "Uploaded file cleanup is not automatic").
- **Anyone who is signed in can read a profile picture's display image if they have its address.** `GET /api/avatars/:id` checks that you are signed in, not whose picture it is, and not whether it is the one in use: a picture its owner replaced stays readable by its address until it is deleted. The address is a random id, and the original file is only ever readable by its owner.
- **A changed profile picture or display name reaches the people on a note you have open only after that note reconnects.** The picture and name others see on your cursor and at the top of the note are the ones your account had when your connection to that note was set up. A note you already have open keeps showing the old ones until you reopen or reload it, or until its connection drops and comes back (#293, #312).
- **A profile picture appears only in some places.** It shows in the account menu, in the avatars at the top of a note for the people on it, in the picture section of Settings, in a note's share list, in the email suggestions, in a group's member list, in the site admin's user list, in the version history and in the AI edit history. Elsewhere, such as the "last edited by" line in a note's header, a group's storage list and the trash, people are shown by name only; a public link page shows no people at all, and an AI agent among the avatars at the top of a note is drawn as a sparkle. In the version history and the AI edit history, an entry written through an AI agent shows the picture of the person whose account it was written with, not an agent icon.
- **A list that is already open shows someone's changed picture only when it is fetched again.** A share list, member list, user list, version history or AI edit history shows a new picture after you reopen it, reload the page or come back to the window from another one.
- **A sign-in service's picture is downloaded without pinning the address.** The server looks the picture's host name up and checks that the result isn't an internal address, then connects with a second lookup. A host whose DNS answers differently between the two (DNS rebinding) can get past the check, so someone who can set the `picture` their identity provider reports can make the server send a GET request, without cookies or credentials, to an internal address on port 80, 443 or the issuer's port. Only a PNG, JPEG or WebP answer is kept, and it then becomes that person's picture, readable by them; any other answer is discarded. The risk is accepted rather than closed.
- **What a sign-in service's picture can be.** Only `http` and `https` addresses on port 80, 443 or the sign-in service's own port are fetched, and an address that resolves to an internal place (private, loopback, link-local and the like) is refused, except when the picture's host name is exactly the sign-in service's own host name (the same text as its issuer's host name, sub-domains don't count); on that host ports 80, 443 and the issuer's port can be reached, so the same kind of request can reach whatever answers there. A service that keeps its pictures on a different internal host therefore gives no picture. The server doesn't sign in when it fetches, so a picture that can only be read when signed in gives none either. The `picture` claim is taken from the ID token; one that appears only in the userinfo response is read only when the ID token has no `email` claim (the only time that response is asked for). A picture over 1 MiB, one that isn't PNG, JPEG or WebP, one that takes over 10 seconds, or one behind more than three redirects gives none either. A picture that can't be fetched is not an error: signing in works and the person has no picture from it.
- **A sign-in linked on the Link your sign-in page gets its picture at its next sign-in.** When a first sign-in is linked to an existing account on the **Link your sign-in** page, with the account's password or by signing in with a sign-in service already linked to it, no picture is fetched for either sign-in then; the next sign-in with each one fetches its picture.
- **Until your browser has made the display image of a sign-in picture, other people see your initial.** The server fetches the picture, and your own browser cuts the square display image the next time Knotebook is open; others can't read the picture before that. Someone who only uses Knotebook through an AI assistant or the API, and never opens it in a browser, keeps the initial. Opening the crop window while your browser is sending that display image, and then saving, can fail with "This picture was updated elsewhere. Open it again to adjust."; open it again and adjust once more.
- **Cropping a profile picture needs a recent browser.** The browser turns a phone photo upright with `createImageBitmap`'s `imageOrientation: "from-image"`, which needs Chrome 112, Firefox 111 or Safari 16 or later. In an older browser the crop window still opens, but Save says it couldn't read the image. A person on one of those can still use a picture another browser uploaded.
