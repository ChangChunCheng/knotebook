# Changelog: 0.10

Releases in the 0.10 series of Knotebook. Newer releases and changes not released yet are in [CHANGELOG.md](../../CHANGELOG.md).

## [0.10.0] - 2026-10-11

### Upgrade notes

The full checklist is under **Upgrading to v0.10** in [Upgrading and rolling back](../self-hosting.md#upgrading-and-rolling-back).

- **Back up the database first.** This release's database migrations (0020: drop note self-links; 0021: `notes:move` scope; 0022: last sign-in time; 0023: who takes up group space) run automatically when the new server starts. 0020 only deletes rows of `note_links` that record a note as linking to itself — rows a note id written with uppercase letters could create, and that were never correct — 0021 only lets the `scope` of tokens, app credentials and pending authorizations also be `notes:read notes:write notes:move`, without changing any stored value, 0022 only adds a column to `users`, and 0023 only adds a column to `uploads` and fills it in from who uploaded each file; but take a dump before you start the new version anyway, for example `docker compose exec -T db pg_dump -U knotebook knotebook > knotebook-before-upgrade.sql`. Rolling back to 0.9 is harmless for the database; what 0.9 then does with `notes:move`, and how files added while it runs are counted in a group's storage, is in the checklist.
- Migration 0022 adds the time each account last signed in. Nothing is filled in for existing accounts: until someone signs in again, the admin API reports `lastLoginAt: null` for them, the same as for an account that has never signed in.
- Migration 0023 records who brought each attachment into its space — whoever uploaded it, or whoever moved or copied its note into a group — and a group's storage **By member**, new in this release, counts by it. Existing attachments are filled in with whoever uploaded them: moves made before the upgrade weren't recorded, so the files of notes moved into a group before then still count for the people who uploaded them. Copies made before the upgrade already count for the person who copied them, because a copy has always recorded the copier as the uploader of the files it copies.
- MCP: every tool now rejects an argument it doesn't know. Until now only `create_note`, `move_note_to_group` and `copy_note` did; the other seven tools dropped it silently. A client or script that sends an extra or misspelled argument — `ifMatch` instead of `if_match`, say — now gets an input-check error (an `isError` result with no `code`) and the tool does nothing; fix the argument's name. The tool list a client sees is unchanged by this.
- **Existing tokens and apps can no longer call `move_note_to_group`, or `copy_note` with `group_id`:** both now need the new `notes:move` scope, which no existing credential has. To allow it, turn on "Move or copy notes into groups" (with "Create and edit notes") for the token or app on its row in Settings → Authorization → API tokens, then restart the MCP client; or authorize the app again and tick both (the second box appears only if the app asks for `notes:move`; an MCP client that follows the `/api/mcp` challenge does); an existing credential's scope can also be changed with `PATCH /api/auth/tokens/:id` from a signed-in browser session (#239).
- **Apps you authorize for the first time are read-only by default.** On the consent page, tick "Create and edit notes" to let an app write: pressing Allow straight away now gives it read-only access, where before it got everything it asked for. Re-authorizing an app starts from the access it already has, never more than it is asking for this time. Personal API tokens were already read-only by default; the Create API token dialog now has a checkbox for each permission, both unticked to start (#239).
- MCP clients cache their tool list; after changing a credential's access, restart the client to see the change (#239).
- A consent page left open from before the upgrade answers Allow with an error; reload it and choose again (#239).
- The first `docker compose up -d` with the new `docker-compose.yml` re-creates the bundled `db` container, because its healthcheck changed; the data in the `db_data` volume is kept.

### Added

- Version history: **All** and **Manual only** buttons above the version list (and above the full-screen list on a narrow window) switch between every version and only those saved by hand or automatic ones whose name was edited (that turns them into manual versions). The two menus used to pick the versions to compare follow the choice; a version you are previewing or comparing isn't affected by it. The choice is the same for every note and is remembered in the browser. `GET /api/notes/:id/versions` accepts `kind=manual` or `kind=auto` to list only that kind (400 `invalid_body` for anything else); it combines with `before` and `limit` (#258).
- `notes:move` scope: with a token or app credential, moving a note into a group (`move_note_to_group`) and copying one into a group (`copy_note` with `group_id`) need it, on top of `notes:write`. It is off unless you ask for it (#239).
- The Create API token dialog has a switch for each permission — "Create and edit notes" and "Move or copy notes into groups" — both off to start, and the token list shows a third kind of access (#239, #247).
- The consent page lets you choose each permission the app asks for; when you authorize the same app again, it starts from the access the app already has and marks it "Currently granted" (#239).
- `PATCH /api/auth/tokens/:id` accepts `scope`, to raise or lower an existing token's or app's access from a signed-in browser session; it applies from the credential's next request. Settings → Authorization does the same from the pencil on each token's row (#239, #247).
- Self-hosting with your own PostgreSQL: set `BUNDLED_DB=0` in `.env` and point `DATABASE_URL` at your server, and `docker compose up -d` no longer starts the bundled `db` container. Leaving `BUNDLED_DB` unset keeps the bundled database, as before. Inside the `app` container, `host.docker.internal` now points at the machine running Docker, for a PostgreSQL running there (see [Using your own PostgreSQL](../self-hosting.md#using-your-own-postgresql)).
- API: `GET /api/storage` and `GET /api/groups/:id/storage` also return `byKind`, the bytes of uploads of each kind (image, audio, video, document, other); the group endpoint also returns `byMember`, how much of the group's space each person has taken up: the files they uploaded into its notes, every file of a note they moved into the group, and the files copied with a note they copied into it (#247).
- API: `PATCH /api/auth/profile` accepts `displayName` to change the name others see; it follows the same rule as registering and doesn't count against the rename limit (#247).
- API: `POST /api/admin/users/:id/demote` removes a user's site admin role. It refuses to remove your own (`400 cannot_demote_self`) or when no other enabled admin would be left (`409 last_site_admin`) (#247).
- API: `GET /api/admin/users` returns `lastLoginAt`, when each user last signed in (`null` if they haven't since upgrading). A sign-in made while another change to the same account is in progress can go unrecorded (#247).
- Group storage shows usage by file type and by member, and every member of the group can see it (#247).
- You can change your display name — the name others see — in **Settings → Account info** (#247).

### Changed

- Version history: an automatic version now shows a grey **Auto-saved** tag next to its number; the row no longer spells out "Manual" or "Auto" and no longer has the green dot on the base version. The line under **Current state** now reads **Based on vN · no changes** or **Based on vN · unsaved changes** (or **No base version**), whichever versions the list shows, and a row's "continued from vN" reads "based on vN" (#258).
- Version history: opening another note while the list beside the note is open (wide window) keeps it open and shows that note's versions, instead of closing it. It still closes when the other note can't be edited by you; the full-screen history on a narrow window still closes when you open another note (#258).
- **Breaking (MCP):** `move_note_to_group` and `copy_note` with `group_id` need the `notes:move` scope. A credential without it isn't offered `move_note_to_group`, and its `copy_note` answers `insufficient_scope` when given `group_id`, copying nothing; its `copy_note` description says so (#239).
- **Breaking (API):** `POST /api/oauth/decision` requires `scope` — what was ticked — when allowing, and grants the narrower of it and what the app asked for; an Allow without it is `400`. `GET /api/oauth/request` also returns `existingScope` (#239).
- `POST /api/auth/tokens` accepts `notes:read notes:write` and `notes:read notes:write notes:move` as `scope`; `notes:write` is still accepted for `notes:read notes:write` (#239).
- The `/api/mcp` challenge and both OAuth metadata documents list `notes:move` (#239).
- The read-only MCP `instructions` now tell the assistant to ask the user to turn on "Create and edit notes" for the credential on its row in Settings → Authorization and then reconnect (#239, #247).
- **Breaking (MCP):** `list_notes`, `search_notes`, `read_note_outline`, `read_note_section`, `edit_note`, `create_transfer_token` and `read_note_image` reject arguments they don't know instead of ignoring them. Before, `edit_note`'s `append` with `ifMatch` instead of `if_match` skipped the fingerprint check and wrote anyway (#241).
- API: any member of a group can now read `GET /api/groups/:id/storage`; before, only roles that can manage the group could (others got `403`). Someone who isn't a member still gets `404` (#247).
- After linking a sign-in service from Settings, the browser now comes back to `/settings/login` (`?linked=` or `?link_error=`) instead of `/settings/account` (#247).
- **Settings has six pages:** **Account info** (display name and URL name), **Sign-in** (password and linked sign-in services), **Authorization** (API tokens and the apps you've authorized, and how to connect Claude over MCP), **Groups** (your groups, with your role and its permissions in each), **Storage** (your usage, by type, and the switch for automatic versions of your notes) and **About** (#247).
- **Site admin is a panel again**, opened from **Site admin** in the user menu over the page you were on, with five sections: **Users**, **Groups**, **Sign-in** (was `/admin/auth`, now `/admin/login`), **Storage plans** (now also holds the site's version-history settings; `/admin/versions` redirects there) and **AI agents** (was **AI**). Closing it returns to that page, or to the home page if you opened it from a bookmark or a pasted address; the **Back to notes** link is gone (#247).
- **Each group has its own panel** at `/groups/<id>` — the group's `⋮` menu in the sidebar → **Members & settings** (or **View members**) — with **Members**, **Roles**, **Storage** and **About**; it no longer lives inside Settings, and `/settings/groups/<id>` redirects there. Leaving or deleting the group from it returns you to the page you were on, or to the home page if that was one of the group's notes or you opened the panel from a bookmark or a pasted address (#247).
- Group roles: a permission switch takes effect as soon as you flip it; there is no **Apply** button. Rename a custom role with the pencil (#247).
- Site admin → Users: the role is a menu (**Admin**/**User**) — choosing **User** removes the admin role, which the web app couldn't do before — and **Enabled** is a switch in place of the **Status** column and the **Disable**/**Enable** buttons; turning it off still asks first. A new **Last sign-in** column shows **Never** until the person next signs in after upgrading (#247).

### Fixed

- The bundled database's healthcheck runs `pg_isready` without a shell and over TCP. When a check timed out, the shell was killed but `pg_isready` was left behind, and if it then gave up without a response, PostgreSQL treated it as a crashed server process and restarted, dropping every open connection; and on the first start the check could report the database ready while it was still being initialized.
- MCP: a `note_id` with uppercase letters now reaches the same live note the web app edits: `read_note_outline` and `read_note_section` return what is being typed rather than the last saved copy, the assistant shows up for people who have the note open whenever it would with a lowercase id, and `edit_note` writes into that note — before, with the note open in the web app, an `append` reported success, but the people editing never received the text, and the note as saved afterwards didn't have it either. `read_note_outline` now answers with the note's id in lowercase (#240).
- API: a note id with uppercase letters in the path of `GET /api/notes/:id/content`, `POST /api/notes/:id/edits`, `GET /api/notes/:id/edits` and `POST /api/notes/:id/edits/:editId/revert` is now treated like the lowercase id: reading the content returns what is being typed rather than the last saved copy and shows the caller to people who have the note open whenever the same read with a lowercase id would, and an edit reaches the note as they have it open; listing edits and reverting one get the same fix (#240).
- API: an uppercase user id in `DELETE /api/notes/:id/shares/:userId` or `DELETE /api/groups/:id/members/:userId`, or an uppercase note id when removing a share, now ends that person's open editing connection the same way a lowercase id does, and deleting a note by an uppercase id now closes everyone's open editing connection to it, as a lowercase id does; other share changes and changing a member's role in a group get the same fix, and `PATCH /api/groups/:id/members/:userId` now answers with the member's id in lowercase. A member who isn't a group manager can now leave a group using their own id in uppercase, which used to be refused (#240).
- API: `POST /api/notes/:id/collab-token` with uppercase letters in the id now issues a token for the lowercase id. Connect to `/collab` with the lowercase id; an uppercase one is now refused instead of opening a separate copy of the note (#240).
- API: `POST /api/notes/:id/links` matches the ids in `link_target_ids` regardless of letter case: the note's own id in capitals is no longer recorded as a link from the note to itself, and one id sent in two letter cases counts once toward the 1000-target limit instead of pushing a request over it with `400`. Upgrading removes self-links already stored (#240).
