# Changelog: 0.7

Releases in the 0.7 series of Knotebook. Newer releases and changes not released yet are in [CHANGELOG.md](../../CHANGELOG.md).

## [0.7.0] - 2026-10-09

### Upgrade notes

- **Back up the database first.** This release's database migrations (0016–0018: the body-text search index, the `transfer_tokens` table, and storage plans) run automatically when the new server starts. The storage-plan migration also gives every existing user and group a plan, so take a dump before you start the new version, for example `docker compose exec -T db pg_dump -U knotebook knotebook > knotebook-before-upgrade.sql` (#93, #200).
- **The first start after upgrading indexes your existing notes in the background.** A new database migration adds the body-text search index, which the server then fills in after it is already answering requests; the `app` log shows `全文索引回填開始` when that starts and `全文索引回填完成` when it is done. Until it gets to a note, `search_notes` finds that note by its title only. Rolling back is harmless — an older server ignores the index — and the next upgrade catches up on whatever was edited in between. See [Upgrading and rolling back](../self-hosting.md#upgrading-and-rolling-back) (#93).
- **`search_notes` is now rate-limited** to 60 searches per minute per user; past that, it answers with the tool error `too_many_requests`. Before, only the limits that apply to every MCP request applied to it (#93).
- **Restart MCP clients to pick up `search_notes`'s new reply shape** (see **Changed** below). A client keeps the tool list it fetched until it restarts, and one that checks replies against the cached output schema can reject the new replies until then — see **A client's cached tool list does not shrink on its own** in [Known limitations](../known-limitations.md) (#93).
- **Everyone starts on a 2 GiB plan.** The migration creates a plan named Basic (2 GiB) and puts every existing user and group on it. Spaces already over 2 GiB keep everything but can't add attachments until they get a larger plan or drop back under the limit — check **Site admin → Users** and **Site admin → Groups** (or `GET /api/admin/users` and `GET /api/admin/groups`) after upgrading.
- **Changes an existing API or MCP client may notice:**
  - Uploads, copies, moves and group transfers can answer `409 storage_quota_exceeded`, and also `409 server_busy` when the storage check can't run in time; `POST /api/admin/users` and `POST /api/groups` can answer `409 server_busy` when the default plan is deleted at that moment; `GET`/`POST /api/admin/users` responses carry a new `storage` object. Creating a user with `POST /api/admin/users` or a group with `POST /api/groups` now fails with 500 if the `site_settings` row has been removed by hand.
  - An MCP upload token used on a full space is answered `409 storage_quota_exceeded` and stays usable once space is freed.
  - MCP `create_transfer_token` with `purpose: "upload"` answers the tool error `storage_quota_exceeded` instead of issuing a token when the note's storage space is already full.
  - A token or app credential's MCP `tools/list` has one more tool, `create_transfer_token` (a read-only credential is offered it for downloads only); a browser session's does not change (#200).
  - `POST /api/notes/:id/uploads` and `GET /api/uploads/:id` now judge a request carrying an `Authorization` header by that header alone, ignoring the session cookie, as the other token endpoints do; such a request's `401` carries a `WWW-Authenticate` challenge and counts against the per-IP limit on invalid Bearer attempts. Without the header they behave as before (#200).

### Added

- **MCP `search_notes` searches note body text, not just titles.** A note that matches in its body lists up to 3 of the sections that contain your text, each with its `sectionId` (which `read_note_section` takes), its heading and a short excerpt. See [MCP](../mcp.md#search_notes) (#93).
- MCP tool `create_transfer_token`: an assistant can upload an image to a note, or download a note's images, with a short-lived token and a ready-made `curl` command — its MCP credential can't be sent from a shell, and image bytes don't fit in tool arguments. Upload tokens need `notes:write` and edit access, are good for one file and at most 5 can be unused at once per credential; download tokens work any number of times on one note's uploads. Tokens expire within 10 minutes, and revoking the credential that issued them ends them (#200).
- MCP and the API can read and write text and background colors. Reading a note returns colored text as a `<span style="color:red">` inside the Markdown, and paragraphs, headings, list items, quotes and table cells that have a color of their own as HTML with `data-text-color` / `data-background-color`, instead of dropping the colors, so writing back what was read keeps them; content without colors reads back exactly as before. Writing accepts the same HTML, and only the editor's ten built-in color names: any other color value is now rejected whole with the new error code `unsupported_color` (before, it was stored but never shown). See [AI editing](../ai-editing.md#colors) (#222).
- **Storage quotas.** Every personal space and every group has a storage plan, which can limit the total size of its attachments (or set no limit); uploads, copies, moves into a group and group transfers that would go over the limit are refused with `409 storage_quota_exceeded` (nothing already stored is ever deleted). Site admins manage plans, the defaults for new users and new groups, and assignments through `/api/admin/storage-plans`, `/api/admin/users/:id/storage-plan` and `/api/admin/groups/:id/storage-plan`; `GET /api/admin/groups` lists every group with its usage. Users see their own usage at `GET /api/storage`, group managers their group's at `GET /api/groups/:id/storage`.
- **Storage quotas in the web app.** **Site admin → Storage plans** lists every plan with its limit, how many users and groups are on it and how many of them are over it, and lets you create, edit and delete plans and choose the defaults for new users and new groups; **Site admin → Users** gains **Storage** and **Plan** columns, and the new **Site admin → Groups** lists every group with its member count, usage and plan — pick a plan in a row to assign it. **Settings → Account** shows your own usage, and a group's settings page shows the group's to people whose role can manage it; both warn once usage reaches the limit. When an upload doesn't fit, the notice says the storage is full, with how much is used and the limit when it's your own space, a group you manage, or you're a site admin.
- **Presentation mode.** Any note can be played as a slide show: choose **Present** from the note's ⋮ menu (in the page header or on its row in the sidebar), or the **Present** button on a public link's page. The highest heading level among the note's top-level blocks becomes the slides that run left to right, the next level the slides below them, and a divider starts a new section; the note's title is the cover. Presenting asks for full screen — Esc leaves full screen, Esc again or ✕ goes back to the note — each slide has its own address (`?present#/…`), and signed-in viewers see collaborators' edits while staying on the same slide; on a public link the slides update when the page fetches the note again. See [Known limitations](../known-limitations.md) (#229).

### Changed

- **Move to…** and **Copy to…** are now in a note's `⋮` menu, each with its own icon like the other items, instead of the **Move or copy into a group** row of the Share dialog, which is gone. Groups are offered only where your role can both create and edit notes. On your own personal note, **Copy to…** starts with **Make a copy**; on a group note there is no **Move to…**, and **Copy to…** offers **Make a copy** (in the same group), **Personal space** and your other groups; on a note shared with you (as a viewer or an editor) it offers **Personal space** and your groups, and no **Move to…**. This replaces the `⋮` item **Copy to my notes** and the **Copy to my notes** button in a group note's Share dialog. Hover an item to open the list beside the menu; on a narrow window or a touch screen it expands right below the item instead. Choosing a target opens a confirmation, and a finished move shows a "Moved into …" notice (#216).
- `search_notes` replies have a new shape: the top-level `matchedOn` is gone; each note carries its own `matchedOn` (`title`, `body` or `both`) and `matches`, and the reply carries `matchesTruncated: true` when some matches were left out to keep it small. Notes that match only in their body come after every note whose title matches (#93).
- `POST /api/notes/:id/uploads` and `GET /api/uploads/:id` accept a transfer token as `Authorization: Bearer knbt_…` in addition to the session cookie; on these two endpoints a request carrying an `Authorization` header is judged by that header alone and the cookie is ignored. An ordinary API token is still refused there, now with a `401` that points at `create_transfer_token` (#200).

### Fixed

- Browser tabs and iOS home-screen shortcuts now show the Knotebook icon (the sidebar's italic "K") instead of a blank default icon.
- The last-edited line at the top of a note now updates a few seconds after you edit the note yourself; before, it only followed other people's edits, and your own showed up only after reloading the page.
