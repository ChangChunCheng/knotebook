# Changelog: 0.15

Releases in the 0.15 series of Knotebook. Newer releases and changes not released yet are in [CHANGELOG.md](../../CHANGELOG.md).

## [0.15.0] - 2026-11-10

### Upgrade notes

- **Migration 0036 (MCP bulk transfer) only adds tables and columns and changes checks**: `transfer_tokens` gets `access` and `range` and its `note_id` may now be empty, two tables are new (`transfer_bases` and `transfer_creates`), and the AI edit history allows the `op` `file_sync`. Existing rows are left as they are. Back up the database first as usual. See [Self-hosting](../self-hosting.md#upgrading-and-rolling-back).
- **Migration 0037 (MCP bulk transfer) only adds one column**: `transfer_bases` gets `applied_edit_ids`, the AI edit history rows a downloaded copy wrote when it was sent back, so that a file whose rows were reverted is refused with `409 base_unavailable` (`reason: "reverted"`). Existing rows are left empty, which counts as nothing reverted. See [Self-hosting](../self-hosting.md#upgrading-and-rolling-back).
- **Restart your MCP clients** to see `create_bulk_transfer_token`: a token or app credential gets it on a deployment with the collaboration component. No credential's scope changes.
- ⚠ **Rolling back to v0.14:** **Don't revert the AI edit history rows of files sent back over MCP while v0.14 runs.** In v0.14, a `file_sync` row for a part a file rewrote or added can show a **Revert** button, and reverting it reports success but puts nothing back; the row is then marked as reverted, so it can't be reverted after upgrading again either. To undo such a write, upgrade again first, then revert it. See [Self-hosting](../self-hosting.md#upgrading-and-rolling-back) and [Known limitations](../known-limitations.md#sending-notes-back-as-files-mcp-bulk-transfer).
- **After `APP_SECRET` changes, notes downloaded as files have to be downloaded again**: sending back a copy downloaded before the change answers `409 base_unavailable`.
- **Breaking for MCP clients: `edit_note`'s `rename` now needs `if_match`**, the fingerprint of the title it replaces, which `read_note_outline` now returns as `titleFingerprint` (a successful rename returns the new title's). A rename without `if_match` — until now the only form accepted — is refused with `invalid_body`; one whose `if_match` isn't the current title's fingerprint, because someone changed the title after the client read it, is refused with `fingerprint_mismatch` and leaves that title as it is. Before, an assistant's rename silently overwrote a title someone else had just changed. The content operations' `if_match` is unaffected: a title change doesn't change any content fingerprint. Renaming a note in the web app works as before. See [MCP](../mcp.md#rename) (#381).
- **Breaking for MCP clients and the API: Markdown with a `<script>`, `<style>`, `<iframe>`, `<object>`, `<noscript>`, `<title>` or `<template>` element is now refused.** `edit_note` and `create_note`, `POST /api/notes` with `content`, and `POST /api/notes/:id/edits` answer `unsupported_block` and write nothing, wherever in the Markdown such an element is; before, the element was silently dropped along with everything inside it, and the rest was written. The same text inside a code block or an HTML comment, or escaped (`&lt;script&gt;`), isn't an element and is still accepted. Files sent back over MCP bulk transfer are refused the same way. If a client of yours writes HTML like this, have it leave those elements out. See [AI editing](../ai-editing.md#markdown-round-trip).
- **Breaking for MCP clients and the API: Markdown with a paragraph inside another paragraph, or nested more than 128 HTML elements deep, is now refused** with `unsupported_block`, by the same endpoints and tools and by files sent back over MCP bulk transfer, and nothing is written. A paragraph can only end up inside another through HTML, such as a `<p>` inside a `<button>`, `<marquee>`, `<svg>` or `<math>` that is itself in a `<p>`; before, its text could be written twice. The depth counts each HTML element, the paragraph inside included, so a quote is one level and a list level two: quotes nested 127 levels deep and lists nested 63 levels deep still fit, 128 and 64 don't. Both kinds of content could keep the server busy for many seconds. Markdown nested several thousand levels deep, which could run the server out of memory, now runs into the time limit for reading Markdown instead (see the next note). See [AI editing](../ai-editing.md#markdown-round-trip).
- **Breaking for MCP clients and the API: Markdown that takes the server longer than 10 seconds or more than 1024 MiB of memory to read is now refused** with `unsupported_block` and a message saying the content is too complex, and nothing is written — by `edit_note`, `create_note`, `POST /api/notes` with `content`, `POST /api/notes/:id/edits` and files sent back or created over MCP bulk transfer (the file answers `400`). Ordinary notes are far from it: 256 KB of formatted Markdown takes about 1.4 seconds. What reaches it is dense formatting inside quotes or `<details>` nested a few levels deep (256 KB of bold words inside quotes nested 5 levels needs about 1.5 GiB) and Markdown nested several thousand levels deep; such writes used to freeze the whole server while they were read, or crash it. These writes can also now answer **`server_busy`** (HTTP `503` with `Retry-After`) when they have waited for a parse worker for 45 seconds (by default 4 × `PARSE_TIMEOUT_MS` + 5 seconds, so that waiting behind one job running to its time limit is enough); nothing is written, try again — `POST /api/notes` with `content` and `create_note`, which never answered `server_busy` for a busy queue before, can now. All four numbers can be set: see the next note and [Self-hosting](../self-hosting.md#parse-workers) (#398).
- **Breaking for MCP clients and the API: reading a note can now fail, and a write can be refused because someone is typing.** Turning a note into Markdown happens in a parse worker with a time limit of three times `PARSE_TIMEOUT_MS` (30 seconds by default) and the worker's memory limit: a note that needs more — measured, a 10 MB note took about 10 seconds — answers `500 too_complex` from `GET /api/notes/:id/content` and the single-note fetch of bulk transfer, the tool error `too_complex` from `read_note_section` and `read_note_outline`, and is left out of a bulk download (listed as `skipped`, `failed`); putting a write or revert into such a note answers `500 too_complex` (MCP: `too_complex`). Reads also answer **`503 server_busy`** with `Retry-After` when they wait longer than `PARSE_QUEUE_WAIT_MS` for a worker, and a bulk download lists notes it couldn't get a worker for as `skipped`, `busy`. A write (and a revert) is worked out against the note as it is; changes others make meanwhile to other parts of the note are merged with it, while a change to the section its `if_match` names makes it start over (and answer `409` if the section now differs). If that section keeps being touched but ends up the same, after three tries it answers `503 server_busy` with `Retry-After` and writes nothing; a file sent back needs the whole note unchanged, and after three tries answers `503 server_busy` without `Retry-After`. See [Known limitations](../known-limitations.md) (#398).
- **Breaking for MCP clients and the API: a note can grow to at most 5 MiB of stored state.** A change that would make a note larger than `NOTE_MAX_BYTES` (5 242 880 bytes by default) and larger than it was, and that adds content (judged on the result: the text, attributes, formatting and other values still in the note, as stored) or grows its stored state by more than 4 KiB at once, is refused with `413 note_too_large` (MCP: the tool error `note_too_large`), carrying the limit as `limitBytes`, and nothing is written — from `edit_note`, `create_note` with `content` (no note is created), `copy_note` and copying in the web app, `POST /api/notes` with `content`, `POST /api/notes/:id/edits`, reverting an edit, applying a note version, and files sent back or created over MCP bulk transfer. In the web app the limit is a soft check made by the editor: before pasting, dropping content in or applying an AI action's result, it estimates how much the note would grow and, if that would take it over the limit, adds nothing and says so. The estimate is close but not exact (measured at about 0.94–1.15 times the real growth), so a note can end up modestly over the limit; typing isn't blocked, and a note over the limit shows a notice that editing may be slow and that deleting content shrinks it. The server doesn't check the browser's live edits, so a custom collaboration client can bypass the limit; see [Known limitations](../known-limitations.md). Notes already larger still open, read, download and export; deleting, and replacing content with the same number of bytes or fewer, are always accepted, while formatting text or adding to it is not; nothing is cut or moved automatically. See [Self-hosting](../self-hosting.md#note-size) and [Known limitations](../known-limitations.md).
- **The server process now runs parse workers, which use memory of their own**: about 120 MB each when idle, and up to about the memory limit (`PARSE_WORKER_MEMORY_MB`, default 1024 MiB) while reading heavy Markdown. Unless `PARSE_WORKERS` is set, the server runs one less than the number of CPUs (at most 4), but no more than half its memory divided by `PARSE_WORKER_MEMORY_MB`, and at least one — so a machine with 2 CPUs, or with 2 GiB, runs one. In a container, the CPUs and memory counted are its limits (cgroup), not the host's; `docker-compose.yml` now has a commented-out `deploy.resources.limits` example. On a 2 GiB machine, set `PARSE_WORKER_MEMORY_MB` to 512. [Self-hosting](../self-hosting.md#parse-workers) has a formula and worked values for 2, 4, 8 and 16 GiB.
- **Reading a note gives slightly different Markdown** (#386): `read_note_section`, `GET /api/notes/:id/content` and notes downloaded with MCP bulk transfer now put a backslash before `*`, backticks, brackets, `_` and `~` in the text and before a block marker at the start of a paragraph (`\# x`), give some line breaks as `<br>`, and put spaces at the edges of bold, italic and struck-through text outside the markers (` **b**`). Writing that Markdown back gives the same text, but **scripts that compare the text they read with fixed strings need updating.** See [AI editing](../ai-editing.md#markdown-round-trip).
- **A file sent back over MCP bulk transfer can be at most 262 144 bytes (256 KiB)**, the same as the request body limit of `edit_note` and `POST /api/notes/:id/edits`; until now (in this unreleased feature) it was 1 048 576 bytes. A larger file answers `413 content_too_large`, and a note whose downloaded file is larger is marked `tooLargeToSend: true` in the download's manifest: split it into smaller notes or change it with `edit_note`. A large file dense with formatting takes many seconds to read, which is why the limit is lower. See [MCP](../mcp.md#limits).

### Added

- **Four settings for reading written Markdown**: `PARSE_WORKERS` (how many parse workers; default the smaller of one less than the CPUs (at most 4) and half the memory divided by `PARSE_WORKER_MEMORY_MB`, at least 1), `PARSE_WORKER_MEMORY_MB` (each worker's memory limit, default 1024), `PARSE_TIMEOUT_MS` (how long one write's Markdown may take to read, default 10000) and `PARSE_QUEUE_WAIT_MS` (how long a read or write may wait for a free worker; unset, 4 × `PARSE_TIMEOUT_MS` + 5000, which is 45000 by default). Out-of-range values stop the server from starting, and the values in effect are logged at startup, with whether the number of workers came from the setting, the CPUs or the memory, and the CPUs and memory found. In a container, the CPUs and memory counted are the container's limits (from its cgroup), not the host's. See [Self-hosting](../self-hosting.md#parse-workers) for how to choose them (#398).
- **`NOTE_MAX_BYTES`**: the largest a note may grow to, in bytes of its stored state (default 5 242 880, 5 MiB; 1 to 1 073 741 824; out-of-range values stop the server from starting). When it starts, the server logs how many notes are already over it and their ids (not their titles). The web editor reads it from `GET /api/auth/config` (`noteMaxBytes`) for its own check. See [Self-hosting](../self-hosting.md#note-size).
- **Keyboard shortcuts**: press Ctrl+/ (⌘/ on a Mac), or choose **Keyboard shortcuts** in the user menu at the bottom of the sidebar, to see the common keyboard shortcuts and typing triggers. It looks like the settings: the groups (General, Typing triggers, Markdown shortcuts and so on) are listed on the left and the shortcuts of the chosen group are on the right, one group at a time; on a narrow screen the two take turns. It lists only what your site can use: the AI group isn't shown when no AI action is set up, and the line about sending an instruction isn't shown when there is no Instruct action. Press the shortcut again or Esc to close it. It doesn't open while another dialog or menu is open, during a presentation, or on pages without the sidebar (sign-in, public notes). See [Known limitations](../known-limitations.md#keyboard-shortcuts).
- **Ctrl+, (⌘, on a Mac) opens your settings**, the same as **Settings** in the user menu, which now shows the shortcut next to it. It works on pages that have the sidebar (not sign-in or public notes) and does nothing while another dialog or menu is open, including the settings themselves.
- **Read and write many notes as files over MCP** (`create_bulk_transfer_token`). An assistant gets a short-lived token — at most 30 minutes — and ready-made `curl` commands: one downloads every note you can see, or only your own notes, notes shared with you, one group's or one folder's, as a `.tar.gz` of markdown files in the same folders as the sidebar; one fetches the latest copy of one note; with `notes:write`, one sends a changed file back; and one revokes the token. A file sent back changes the note only in the blocks where it differs from the copy downloaded. If the note has changed since the download — its text or its title — a changed file is refused with `409 base_unavailable` (`reason: "note_changed"`) and nothing is written: download that note again and redo the change. A file with no `id` creates a note, and the same file sent again within 30 minutes doesn't create a second one. Each changed place is a `file_sync` row in the note's AI edit history and can be reverted. Downloads are limited to 10 per person per hour and one at a time on the site, and files sent back to 30 per person per minute (a file whose text or title differs from its downloaded copy, or that creates a note, counts before its text is parsed, so it counts even when its text is then refused; a file refused before that, for example one that isn't UTF-8 or whose front matter is malformed, doesn't count). The commands call `GET /api/transfer/export`, `GET /api/transfer/notes/:id`, `PUT /api/transfer/notes` and `DELETE /api/transfer/token`. See [MCP](../mcp.md#open_notes_as_files), [API](../api.md) and [Known limitations](../known-limitations.md#sending-notes-back-as-files-mcp-bulk-transfer).
- **The sidebar's search also finds notes by their text.** Notes whose title matches and notes whose body text matches are in the same list: a note that matches only by title takes two lines (title and location), and each section whose text matches takes an entry of three lines (the note's title, its location, and the excerpt), up to three sections per note, 20 notes at a time with **Load more**; the section's heading isn't shown. Clicking an entry opens the note, scrolls to the first block of that section that contains the text, in the middle of the note's scrolling area, and marks it: it flashes twice and then stays highlighted until you press Esc, clear the search box, switch sidebar tab (when the box is already empty), click another result or leave the note (closing the drawer on a narrow screen keeps it) (in the note already open, it scrolls there without reloading the page; an entry from before the note's first heading opens the note at the first matching block, or the top if none); on a narrow screen it also closes the navigation drawer. Body text is searched from the second character typed, and these searches count against the same limit of 60 a minute per person as MCP's `search_notes`. See [Known limitations](../known-limitations.md).
- **`GET /api/search`**: search the titles and body text of the notes you can see, with excerpts, `match=body` for body matches only, and pages of up to 50 (`cursor`/`nextCursor`). Takes a session or a token with `notes:read`. See [API](../api.md).
- Test-only: end-to-end tests for files sent back to a note someone has open, a file refused because the note changed, reverting `file_sync` rows and downloading what is being typed (`e2e/tests/45-bulk-transfer.spec.ts`), and three benchmarks for downloading notes and sending files back (`apps/server/test/bench/transfer-*.bench.ts`), which don't run in CI.

### Changed

- **Writing and reading notes over MCP, the API and bulk transfer no longer hold up the server.** The Markdown that `edit_note`, `create_note`, `POST /api/notes` with `content`, `POST /api/notes/:id/edits` and files sent back or created over MCP bulk transfer carry is now read in parse workers, threads of their own with their own memory limit; putting the result into the note, reverting such a write, and turning a note back into Markdown (`read_note_section`, `read_note_outline`, `GET /api/notes/:id/content`, the current content sent with a `409`, and notes fetched or downloaded over bulk transfer) happen there too. Other people's requests and live editing keep running meanwhile: measured on Linux, reading back a note of 1 MB, or a paragraph of 49 000 `<br>`-separated words, used to stop everything for 1.2–5.3 seconds and now for at most about 0.15 seconds, and the heaviest 245 KB writes for 0.6–2.1 seconds and now 0.2–0.45 seconds. The answers themselves take about as long as before. Small notes (under 16 KiB stored) are still handled in the server's own thread, where that takes 10–25 milliseconds. One person can use at most two workers at a time, and a second only while nobody else is waiting. Measured on 2 vCPUs, an ordinary note's write takes up to about 0.08 seconds longer than before; 256 KB dense with `<br>` about 0.57 seconds longer and 256 KB of alternating bold and italic about 0.32 seconds longer (#398).
- **AI actions in the editor apply the same checks as writing over MCP or the API** before reading their result: a result with a paragraph inside another paragraph, or nested more than 128 HTML elements deep (quotes 128 levels deep, lists 64), isn't applied, the same as other content the editor can't store, and a quote, heading or collapsible heading with many paragraphs in it is read in one step instead of slowing down with each paragraph.
- **The note header's connection status is shorter, and the avatars of other people on the note are smaller.** If you can edit the note, it now says just **Connected** (it used to add your role, such as “· Owner” or “· Editor”). If you can only read it, it says just **Read-only** instead of “Connected · Viewer · Read-only”, with the same green dot while the connection is healthy. A read-only viewer sees **Read-only** as soon as the connection is up. The warnings are unchanged: Connecting…, Reconnecting…, Access revoked, Note deleted and Reload required, and the three offline warnings — “Not loaded — offline”, “Editing offline — changes not synced yet” and “Offline” — which turn red after 3 seconds. Your own role is no longer shown in the header; for a note shared with you it is still marked Editor or Viewer in the sidebar’s “Shared with me” list, and for a group note you can see it in the group’s members table. The avatars in the header are 24px instead of 28px, and so is the “+N” button.
- **The sidebar's search count** now says “N title matches” (in Chinese, “標題符合 · N 篇”) until the body-text results have arrived, instead of “N results”; once the body-text results have arrived it says “N results” (“N 筆結果”), counting the entries in the list, and “N results loaded, more available” when there is a next page.
- **What you typed in the sidebar search box is kept** when you go between the home page and a note (for example after clicking a result), so clearing the box afterwards still removes the mark in the note. It is cleared when you sign out or another person signs in.
- **The `429` that `POST /api/notes/:id/uploads` and `GET /api/uploads/:id` answer once invalid Bearer attempts from an address are used up now carries `Retry-After`.** See [API tokens](../api-tokens.md#errors-and-rate-limits).
- **Error messages from the HTTP API are now in English** ([#372](https://github.com/sw-willie-wu/knotebook/issues/372)). The `message` in every `{ "error": { "code", "message" } }` response, the `message` of the AI stream's `error` event, and the `error_description` of the OAuth endpoints were mostly in Chinese (a few were already in English); they are now all in English, written as full sentences that say what went wrong and, where it helps, what to do. The `code` values are unchanged, and the web app, which shows its own text for each `code`, looks the same. A request over an endpoint's size limit (`413 content_too_large`) now gets a message in the same style instead of the server framework's own. **If you have scripts that match the Chinese `message` text, change them to check `code` instead.**

### Fixed

- **Writing or reading a note with a very long paragraph no longer takes time growing with the square of its length** (#398). A paragraph with tens of thousands of line breaks, formatted words or colored stretches — written over MCP, the API or an AI action, or typed — held the whole server up for tens of seconds while it was written or read back: reading one with 24 000 line breaks took 82 seconds, writing one with 49 000 about 42, and replacing it with another such paragraph about 12 more. These now take time in proportion to the content, and run in parse workers (see the change above).
- **A line break inside a paragraph written as Markdown no longer adds a space at the start of the next line** (#386). Markdown sent to `POST /api/notes`, `POST /api/notes/:id/edits`, MCP `create_note` and `edit_note`, files sent back or created over MCP bulk transfer, and the result of an AI action in the editor stored a paragraph of two lines `first` and `second` as "first", a line break, then " second"; the next line now starts with exactly what follows the break, whichever of the three ways the break is written (a plain newline, a backslash or two spaces at the end of the line). Notes already saved with that space keep it — it isn't removed — and now read back as `first<br> second`, so that writing what you read back no longer drops it. Line breaks in list items, table cells and headings also read as `<br>` now: the backslash form read before couldn't be written back there (a list item split into the item and a new paragraph, and a table broke apart). See [AI editing](../ai-editing.md#markdown-round-trip).
- **Writing back what you read no longer turns text into formatting it didn't have** (#386). Reading over MCP or REST, or downloading a note as a file, gave bold, italic or struck-through text that starts with a space as `** b**` (which Markdown doesn't read as bold), left `*`, backticks, brackets, `_` and `~` in the text as they were, and gave a paragraph starting with `# `, `> `, `- `, `+ `, `1. ` or `---` (or a line break followed by such a line) as it was. Writing that Markdown back, or sending the file back, turned them into new bold, code, links, headings, quotes or list items — each round trip changing the text further (in a quote with bold text next to inline code, `**` grew into `***` and the next line became a list item). Now edge spaces of bold, italic and struck-through text, colored or not, read outside the markers (` **b**`); those characters, block markers at the start of a paragraph or quote, and a ` #` at the end of a heading read with a backslash in front (`\*`, `\# x`); and a line break followed by punctuation reads as `<br>`. The text and its formatting then stay the same; only such an edge space is no longer bold, italic, struck through or colored. Text in collapsible list items and headings is covered too, though a collapsible list item written back still becomes a bulleted one. `<` is still not escaped (#379). Notes already changed this way aren't repaired. See [AI editing](../ai-editing.md#markdown-round-trip).
- **Markdown with Windows line endings (`\r\n`) no longer leaves a space at the end of lines**: sent to `POST /api/notes`, `POST /api/notes/:id/edits` or MCP `create_note` and `edit_note`, `first\r\nsecond` was stored as "first " and a line break, and every paragraph ended in a space. `\r\n` and a lone `\r` are now read as `\n`, as they already were when pasting Markdown into the editor (files sent back over MCP bulk transfer already had `\r\n` turned into `\n`).
- **Writing back a link to a note over MCP or the API no longer freezes it to the title the note had when you read it.** A link with no text of its own reads as the linked note's title. If that note was renamed before you wrote that text back unchanged — with `edit_note`, `create_note`, `POST /api/notes/:id/edits` or `POST /api/notes` — the old title used to be saved as the link's own text, so the link stopped following the note's title. The server now remembers, for each account, the text reading showed for such links and the text of such links the account wrote, for up to 24 hours (at most the latest 10 000 for each account) and until it restarts, and that text stays no text of its own; text you changed is still kept as the link's own text. Files sent back with bulk transfer already worked this way and are unchanged. See [MCP](../mcp.md#links-to-notes) and [Known limitations](../known-limitations.md).
- **Presentation overview (O) now shows the content of the slides around the current one**, not just the current one: the others were hidden by the app's base styles, so the overview showed empty frames. The current slide in the overview now has its highlighted outline, and moving between slides in a presentation is an instant switch. See [Known limitations](../known-limitations.md) ([#390](https://github.com/sw-willie-wu/knotebook/issues/390)).
