# Changelog: 0.3

Releases in the 0.3 series of Knotebook. Newer releases and changes not released yet are in [CHANGELOG.md](../../CHANGELOG.md).

## [0.3.3] - 2026-09-02

### Added

- Every account now has a **username** — a short, URL-safe name (lowercase letters, numbers, hyphens) shown and changeable under Settings → Account, for both password and SSO accounts. Existing accounts get one derived from their email's local part on upgrade; SSO sign-ups prefer the identity provider's `preferred_username` claim when the ID token carries it, and admins can set one when creating an account via the API. Renaming is allowed 5 times a day, and a released name is **permanently retired — nobody can ever take it, including you changing your mind** — so links shared under an old name can never start serving someone else's content. The username appears in Settings and the admin user list, and every new-form note URL carries it (`/n/<username>/<slug>` — see the note-URL entry below; old-form `/notes/…` links don't and are rename-proof); it can also appear in a public share's URL when you opt in (see the custom-public-URL entry below).

- Note URLs are now human-readable: `/n/<username>/<slug>` — no uuid suffix. The slug follows the note's title automatically (renaming the note moves its URL, collisions among your own notes get a numeric suffix), or you can pin a custom one in the Share dialog, which now shows the three states honestly: the input is empty unless you've set a custom slug, its placeholder always shows the automatic URL you'd get, and a "Use automatic URL" button appears only when there's a custom slug to give up. Slugs are unique **per user** rather than instance-wide, so `slug_taken` now only ever means another of your own notes. Every previously shared `/notes/…` link keeps working forever (the pre-revamp slug is frozen as a permanent alias, and uuid-suffixed links resolve as before); the sidebar's "current note" highlight now tracks the note itself rather than the URL, so it survives renames. One API-visible behaviour change: `PATCH /api/notes/:id` with `slug: null` now means "back to an automatic slug recomputed from the title" rather than clearing it, and counts against the slug-change rate limit. One upgrade-time note: the migration derives slugs from titles in SQL, which handles ASCII only — a note with a non-ASCII title comes out as `untitled(-n)` and its URL shifts once more, silently, on its first title save afterwards. The other costs that come with human-readable URLs — automatic URLs moving with the title, one level of grace for custom slugs, slug re-use within an account, and username renames breaking `/n/` links — are recorded in [known limitations](../known-limitations.md) (#122).

- A note can now be shared with a public link — anyone who has it can read the note at `/p/<token>`, no account needed. The Share dialog gains an access selector with three levels: **Private** (only you; picking it while members exist asks for confirmation first — covering the link too when one is on — and removes the link before the members so an interrupted switch never leaves the link live; with no members it just turns the link off), **Members only** (the existing email invitations, unchanged), and **Public link**, which shows the URL with copy and regenerate buttons. The public page is strictly read-only, shows the note's title, content and its uploaded images, requires no login, carries `X-Robots-Tag: noindex`, and renders none of the editing machinery; regenerating or turning the link off makes the old URL answer an indistinguishable 404 immediately. The link token is unguessable (256-bit), never appears in server logs, and the public endpoints are rate-limited in a way that doesn't reveal whether a token exists. What anonymous readers see is a snapshot that can lag active editing by a few seconds — the full behaviour, and its recorded trade-offs (Yjs state exposure, cross-note images, browser-cached images after revoke, `TRUST_PROXY` behind a reverse proxy), are documented in [Sharing](../sharing.md) and [known limitations](../known-limitations.md) (#72).

- A public share can now also have a **custom public URL**: `/p/<username>/<name-you-choose>`, set from a new row in the Share dialog while the public link is on. It serves the same read-only page as the token link (images included) and is an addition, not a replacement — the token link keeps working, **Regenerate link** replaces the token without touching the custom URL, removing the custom URL leaves the token alive, and switching to Members only/Private deletes both. The trade-off is spelled out in the dialog itself: a readable URL is a guessable URL, and it reveals your username — for anonymous sharing, use the token link. Names are unique per account (yours can't collide with another user's), validated like note slugs, and share the slug-change rate limit. Renaming your account kills the old custom URL immediately (old usernames are never forwarded) — the name itself survives and keeps serving under your new username. The custom-URL page carries the same `noindex` and the same indistinguishable-404 discipline as the token page; the finer print (username disclosure, doubled read quota for a note reachable both ways) is in [Sharing](../sharing.md) and [known limitations](../known-limitations.md) (#122).

- Knotebook now sends a Content-Security-Policy with the page. A script injected into a note's content does not run, plugin content (`<object>`/`<embed>`) is refused, `fetch`/XHR/WebSocket can only reach Knotebook itself, and the app can no longer be framed by another site. Images, audio and video embedded by URL keep working, over both http and https — that is a deliberate policy choice, since a note can already reference an external image on purpose, and the same holds for diagrams; a note's content can therefore still cause requests to an outside host by referencing one. Two consequences worth knowing if you self-host: stylesheets, fonts and scripts have to come from Knotebook itself, so a reverse proxy that injects an analytics script into the page, or assets moved to a separate CDN, will be blocked, and Knotebook can no longer be embedded in an iframe — see [Self-hosting](../self-hosting.md#content-security-policy). Pages also carry `Referrer-Policy: no-referrer`, so a site hosting an image you embedded no longer learns which note is being read, and `X-Content-Type-Options: nosniff` (#101).

### Changed

- A code block's language dropdown now appears above the block, at its right edge, when you hover the block — the same place and the same behaviour as a diagram's Edit button, in the same small bordered style. It used to sit inside the block's top-left corner, overlapping the start of the first line, which is where you usually click to put the cursor. Keyboard users still reach it by tabbing (focus reveals it). On a note you can only read, it drops its border and background so that hovering the block reveals a plain language label rather than a control you cannot use, since the dropdown is disabled there anyway. Opening it now shows a menu styled like the app's other menus — same surface, border, radius and hover highlight — with a caret on the control that flips when the list is open, in browsers that support customizable selects (Chromium 135+, Safari 27). Where they do not (Firefox today), the browser keeps its own native menu, whose options now at least follow the light/dark theme instead of BlockNote's hard-coded black, which was unreadable against a dark menu (#111).

- A note's title row and the backlinks row span the full card width — title on the left, controls on the right — while the text keeps its centred column. Earlier in this unreleased cycle the two rows had been moved into the text's centred column to line their left edges up (#88); that alignment never shipped and is superseded by this layout revamp, which returns the ~100px of title room the alignment cost on a narrow window and removes the few-pixel scrollbar offset it carried. On a window narrower than 768px the note text's side inset also shrinks from 70px to 20px, so the text and the title share one left edge exactly where the horizontal space is scarce; one cost of that, hover handles clipping on a narrow window, is recorded in [known limitations](../known-limitations.md) (#115).

- Knotebook now works on a narrow window (below 768px). The sidebar hides and becomes a slide-in drawer — opened from a hamburger button in the note's title row, or from a small top bar on pages without one — closing on Escape, on tapping the backdrop, or when you pick a note; Ctrl/Cmd+K opens it with the search box focused. The note text's side inset shrinks so the width goes to your writing, the connection badge collapses to its status dot (screen readers still hear the full text), and the sidebar's note rows grow to a comfortable touch size. One window width is the single breakpoint for all of it (#115).

- The AI entry point is now a round floating button at the bottom-right of the page instead of a collapsed rail beside the note. Clicking it opens the same action list as before — beside the note on a wide window, or as a full-width sheet rising from the bottom on a narrow one, replacing the old right-hand drawer there. The button fades out while you scroll the note and returns when you stop, and keyboard focus always makes it visible; the backlinks row keeps a little end padding so its last chip can scroll clear of the button (#115).

### Fixed

- The public share page now fills the browser window like the rest of the app, instead of floating as a width-capped rounded card that left background margins on wide screens — and the whole page is one flat surface, with no visible content-column "card" either (the page ground now matches the editor's own background color, in both themes). Text line length is unchanged — the reading column is still centered and capped.

## [0.3.2] - 2026-08-31

### Added

- Code blocks now have syntax highlighting. Pick a language from the dropdown in the block's top-left corner — it used to be empty — or type it in a ``` fence (aliases like ```py and ```ts work); 23 languages are included, from TypeScript and Python to SQL, YAML and Dockerfile. Colors are semantic — keywords, strings, comments — with one palette for the light theme and one for dark, switching instantly with the theme; the accent color you chose does not affect them. In light mode a code block is no longer a hard-coded dark box: it now sits on a light grey background with a border, like other surfaces. Copying or exporting a code block still produces the plain source — the coloring never becomes part of the note. The highlighter loads only when a note actually shows a code block, and each language's grammar loads on first use, so notes without code download nothing extra (#96).

- Notes can contain Mermaid diagrams. Insert one with `/diagram` (`/圖表` in Traditional Chinese) from the slash menu, click a diagram to edit its source, then press Escape or click away to draw it again. Pasting a ```mermaid fenced code block turns it into a diagram automatically — including diagrams produced by the AI actions — and the button in a diagram's top-right corner opens the source as well — labelled Edit, or Show source for readers, who get the same text read-only. Diagrams follow the light/dark theme. When the source has a syntax error the block shows the message next to the source, so it stays editable rather than becoming an opaque failure. Copying a diagram out of Knotebook produces the ```mermaid source rather than an SVG, so it renders on GitHub or Obsidian and can still be edited there. A diagram can reference a remote image, the same way a note can embed an image by URL — that is the existing policy for note content rather than something new. What a diagram cannot do is make anything execute: Mermaid runs with `securityLevel: "strict"`, `bindFunctions` is never called, and `themeCSS`/`htmlLabels`/`fontFamily` are locked against a diagram's own init directive so labels stay SVG text. Links a reader can click are kept, marked `rel="noopener noreferrer"`. Mermaid itself is loaded only the first time a note actually draws a diagram, so notes without diagrams download nothing extra (#94).

### Changed

- A selected block now gets a 2px outline in the theme's accent color instead of BlockNote's built-in 4px bright blue. The blue was hard-coded, so it ignored both the light/dark theme and the chosen accent color, and on a large block — an image, a file, a diagram — it read as a thick blue frame around the whole thing rather than a selection cue.
- The backlinks row's horizontal scrollbar is now thinner than the app's other scrollbars (6px instead of 10px) and sits at the very bottom of the row, with a clear gap between it and the chips above. It used to be full-width thickness crowded against the chips in a 36px-tall row, and further from the card's bottom edge than it needed to be.
- In the backlinks row, the horizontal scrollbar now always reserves its space, and the label is aligned to the same optical centre line as the chips. Previously the scrollbar only appeared once there were more chips than fit, and it took its 10px out of the chips' half of the row — so the chips sat about 5px higher than the label exactly when a note had many backlinks (#90).
- The backlinks strip at the bottom of a note is now a single row — the "Mentioned in N notes" label sits inline with the source chips, which scroll sideways when there are more than fit — and it is always present, showing "No mentions yet" when nothing links here. Previously the label sat on its own line above a wrapping list of chips, and the whole strip disappeared when a note had no backlinks, which made the feature invisible on any note nobody had linked to yet and let the note card's height jump around. The row is the same height as the account row at the bottom of the sidebar, so the two line up.

- The note's text column now scales with the window instead of stopping at a fixed 680px: it takes 85% of the scrolling area's width, between 680px and 1056px. Windows up to about 1100px wide keep the column they had — 680px is the floor, and a window narrower than that still gets a full-width column — while on wider screens the article grows with the card instead of sitting as a narrow strip between two large empty margins (#87).

### Fixed

- Redo now works after undoing a note all the way back to empty. Previously, undoing until the note was blank silently discarded the redo history a fraction of a second later — the editor puts the required empty paragraph back into a blank note, and that correction was being recorded as if it were a fresh edit of yours, which is exactly the situation where an editor is supposed to throw redo away. That correction is no longer treated as an edit, and redo brings your text back reliably, including undoing and redoing across the same boundary repeatedly. Deliberately deleting everything in a note is still a normal, undoable edit. This closes the one known gap in the undo fix shipped alongside it (#100).

- Typing `[[` to link another note now works when the two brackets arrive together rather than one at a time. Previously the menu only opened if the editor saw each `[` as its own separate keystroke, so it failed when you typed quickly and the browser batched them, and it failed every time under a Chinese input method — where committing the pending characters sends the whole run, brackets included, as a single edit. The workaround people found (pressing `[` a few more times until one landed on its own) is why it looked intermittent rather than broken. Detection now looks at what sits before the cursor once the input lands, so anything the input method commits alongside the brackets is kept instead of being swallowed. Typing `[` over a selection still replaces the selection and opens the menu, as before (#98).

- Undo works again in the editor. Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z and Ctrl/Cmd+Y did nothing at all — silently, with no error — on every note, in every browser. Notes are collaborative documents, so undo is handled by Yjs rather than by the editor's own history, and the piece of Yjs that records what you changed was being torn down and never reconnected the moment a note finished loading: it stopped listening before you could type your first character. Undo history is per note and only ever takes back your own edits, never a collaborator's. Redo works too, with one exception that is still open: if you undo all the way back to an empty note, redo cannot bring the text back (undo itself is fine, including undoing to empty) — see [Known limitations](../known-limitations.md) and #100 (#97).

## [0.3.1] - 2026-08-26

### Changed

- Scrollbars throughout the app — the note content, the sidebar's note list, the AI panel, the settings dialog and any other scrolling area — are now a thin, rounded, semi-transparent grey that follows the light/dark theme, instead of the operating system's default scrollbar. The track is transparent and the thumb gains contrast on hover (darker in light mode, brighter in dark mode). In Firefox the browser's native thin scrollbar is used, in the same theme-following grey but without the hover effect. On macOS this also means scrollbars are always visible in their own 10px gutter rather than overlaying content and auto-hiding: styling a scrollbar opts that scroll area out of the system's overlay scrollbars (#84).
- The six accent-color dots in the user menu now show which one is selected with a checkmark inside the dot instead of a ring around it — the ring's contrast against the light theme's popover fell short of WCAG's 3:1 minimum, and it shared the same ring slot as the keyboard focus ring, which overrode it, so a focused dot lost its selection cue. The keyboard focus ring itself is unchanged and no longer competes with anything: focus and selection are independent now, so a focused, selected dot shows both at once. The accent-color group of dots also gained an accessible group name (`aria-labelledby`) tied to its "Accent color" heading (#78, #79).
- Traditional Chinese accent color names changed: 青 → 青瓷, 鼠尾草綠 → 鼠尾草, 粉 → 玫瑰. The English names, and the indigo/blue/gold names in both languages, are unchanged (#80).

## [0.3.0] - 2026-08-26

### Changed

- Dark mode's palette is now a neutral dark grey with a slight cool tint, replacing the near-black default, and layered in three visible steps — page background darkest, cards a step lighter, floating surfaces (dialogs, toasts, the BlockNote slash menu/formatting toolbar/tooltips) lighter still — instead of cards and floating surfaces sharing one shade. BlockNote's editor surface and its floating menus now match this scale instead of showing their own built-in dark colors (#75).
- The main layout is now built from cards floating on a deeper background instead of flat, edge-to-edge panels: the sidebar, the note's content, and the AI panel each sit in their own bordered card, while inputs and outline buttons keep the page's background color rather than the card's, so they read as inset into whatever surface they sit on. The sidebar note list now groups into Recent / My notes / Shared with me, with a title search box above it (Ctrl/Cmd+K focuses it, Escape clears it and moves focus away). Deleting a note has moved off the sidebar row and into the note's own ⋮ menu in its header, alongside a new "Copy link" entry; the sidebar itself no longer has a delete button. Backlinks are now a row of chips at the bottom of the note instead of a collapsed section that had to be expanded to see anything. The light theme's page background is now a light grey instead of pure white, to give the new cards something to float on top of — a visible change for anyone using it (#76).
- Knotebook now offers six accent colors — Indigo (the default), Blue, Teal, Sage, Rose and Gold — picked from a row of color dots in the user menu, below the theme setting. The chosen accent tints four places: the "K" wordmark, the sidebar's selected note row, the "New note" button, and a note's share icon. This changes the default look for everyone, not just people who open the picker: those four places used to be neutral and are now tinted Indigo out of the box, and the "New note" button in particular went from a solid filled button to a soft translucent tint of the accent color. As with the theme setting, the choice lives only in this browser's local storage; it is not synced across devices or saved on the server (#77).
